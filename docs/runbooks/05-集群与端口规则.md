# 05 · 集群与端口规则

## 两条互不干扰的起服务方式

| 场景 | 方式 | 端口 |
| --- | --- | --- |
| **门禁 / 测试** | `tests/p0_runtime/conftest.Cluster`（夹具自己起） | **随机空闲端口**（`pick_port`，18100+），进程结束即停 |
| **人工查看后台** | `tools/v3_dev_cluster.py start` | **固定** 8101-8108 |

**为什么必须分开**：要让浏览器里的后台连上，端口必须可预期；
但测试要能并行/重复跑，就必须随机端口。两者用一个方式会互相破坏。

### ⚠️ 由此产生的最容易踩的坑

**门禁必须串行跑。** 夹具起真实多进程集群；
同时再跑一次（前台 + 后台任务 / 两个窗口）会**抢端口** ⇒ **假失败**。

本项目已因此误判**两次**，其中一次还把假失败归因成"代码缺陷"、去改了代码。
排查这类问题的第一步永远是：

```powershell
Get-CimInstance Win32_Process -Filter "Name='python.exe'" |
  Where-Object { $_.CommandLine -match 'pytest|gate\.py|-m services' } |
  Select-Object ProcessId, CommandLine
```

有第二个测试在跑 ⇒ 先清掉再重跑。

**`edge` owner 没有独立服务**：`/edge/v1/**` 在本地由 `manufacturing-core`

（见 ADR-0006）。

## 状态目录

`V3_STATE_DIR`（开发集群用 `.v3-dev/state`）。

**所有单元共享同一个状态目录**——否则跨进程 journal（命令/回执/任务/审计/Vault）
互相看不见，跨服务调用会莫名其妙地"找不到刚建的东西"。

## 常见问题

| 现象 | 原因 / 处理 |
| --- | --- |
| `tools\v3_dev_cluster.py status` 显示 `8/8` 但请求失败 | 检查是不是有**另一个**集群占了同一批端口（先 `stop` 再 `start`） |
| 端口被占（`8101` 起不来） | `Get-NetTCPConnection -LocalPort 8101 -State Listen` 找占用者；或先 `stop` |
| 服务起来了但跨服务调用报"找不到" | 状态目录不一致：确认各单元 `V3_STATE_DIR` 相同 |
| `demo` 报 `复用已在运行的 dev 集群` 后又失败 | 集群在跑但版本旧（改了代码没重启）：`stop` 再 `start` |
| 门禁偶尔红、重跑就绿 | **十个有九个是并发抢端口**；剩下一个查墙钟（见 runbook 02） |

## 为什么 `demo` 不调 `Cluster.start()`

`Cluster.start()` 内部会 `kill_leftovers()`——它把**所有**
`python -m services.*` 进程全局杀掉。在"复用已运行的 dev 集群"模式下，
那会顺手杀掉 dev 集群自己，然后改用随机端口 ⇒ 后台连不上、演示也没了对象。

所以 `demo` 先探测 8101-8108 是否都活着：
活着就**只把端口填进夹具对象**（只连不起），没活着才由夹具自己起一套。
