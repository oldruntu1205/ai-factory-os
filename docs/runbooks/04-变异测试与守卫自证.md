# 04 · 变异测试与"守卫自证"

变异测试回答一个门禁自己回答不了的问题：**这个门禁真的有牙吗？**

「测试全绿」不等于「测试能发现问题」——它也可能只是因为**检查能力为零**。

## 命令

```powershell
cd "H:\制造业 AI 员工平台全量开发"
backend\.venv\Scripts\python.exe scripts\mutate.py --phase {p1|p15|p2|p3|p4}
```

- `[捕获]` —— 注入缺陷后门禁报红（门禁有牙）；
- `[逃逸]` —— 注入缺陷后门禁仍通过（**门禁有盲区，必须回去补测试**）；
- `[无效]` —— 变异没命中原文，或变异后语法不合法。**不计入已捕获**；
- `[已接受]` —— 显式登记的"结构上无法捕获"缺口，必须写明理由。

当前规模：**119 条可捕获变异，全捕获**（另有 5 条已接受缺口）。

## 三条硬规则

### 1. 变异后必须**语法合法**

否则"测试挂掉"是**语法错误导致的**，会被误记成"门禁正确捕获"——
报告说门禁有牙，实际只是文件跑不起来。

`mutate.py` 会先校验：`.py` 用 `ast.parse`，`.js`/`.mjs` 用 `node --check`。
**本条来自真实教训**：我第一版写的 6 条 JS 变异里就有一条括号不配对，
正是被这道校验拦住的。

### 2. 原文必须**唯一**

同形原文出现两次时 `replace(..., 1)` 只改第一处 ⇒ 注入打到**错误的函数**上：
被测路径没变、测试自然绿 ⇒ 误报"逃逸"；更糟的是另一条变异会把这次改动
当成"原文"，于是**静默改坏生产代码**。所以不唯一直接判失败。

### 3. 守卫必须**自证能力**

这是本项目反复踩到的同一个坑，值得单独讲。

**症状**：一条守卫断言"这里没有问题"。它在干净树上永远是绿的——
但那是"真的没问题"，还是"它根本不会识别问题"？**观测上无法区分。**

**实例（仓库卫生守卫）**：把检查改成 `if False` 之后，门禁**照样全绿**。

**实例（领域词表漂移探针）**：第一版只有"实现里的原因码都已登记"一条断言。
变异把探针改成**恒返回空列表**，门禁**照样全绿**。
补了两条自检之后才有效：

```python
# 能力自检：喂构造输入，必须**正好**报出未登记项
assert guard.unregistered_reason_codes(
    ["SOME_FUTURE_CODE", "ANOTHER_FUTURE_CODE:detail", "DRIFT_EXCEEDED"]
) == ["ANOTHER_FUTURE_CODE", "SOME_FUTURE_CODE"]

# 反向自检：全部已登记时必须返回空，不得误报
assert guard.unregistered_reason_codes(list(guard.GUARD_REASON_TO_STAGE)) == []
```

**判据**：能力自检要
① 喂**构造**输入（不是真实数据）；
② 断言**精确结果**（该报的报出来、**不该报的不许出现**）；
③ 样本里**混一个合法项**——否则"全报"也能通过，那同样是能力不足。

## 什么时候该写"已接受"

只有**结构上无法观测**时才写，并且必须说明"为什么观测不到"与
"真实防线在哪里"。当前两条已接受缺口的共同点是：
**门禁根本不运行那段代码**（legacy 的 `backend/tests/*.py` 是独立脚本，
不在 `scripts/gate.py` 范围内）。

反例：**"写起来太麻烦"不是已接受的理由**——那是"该补测试"。

## 修完缺陷的收尾动作

1. 补**回归断言**（钉住修复后的行为）；
2. 补**变异**（让"改回去"这件事被抓住）。

只做第 1 步不够：修复会在下次重构里被无声撤销，而门禁不会报警。
