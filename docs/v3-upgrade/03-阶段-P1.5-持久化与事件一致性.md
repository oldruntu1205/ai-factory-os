## 1. 权威、范围与交付边界

唯一上位文档：[AI Factory V3.0 系统架构](C:/Users/Administrator/Desktop/AI_Factory_V3.0_系统架构.md)，版本 3.0.0。本件细化 §11、§12、§13 中不依赖外部系统的事件与持久化语义，为 §16 的 P2 数据孤岛闭环与 P3 受控写入提供前置。上游规定的是事实、所有权和恢复约束；本件新增路径是这些规定的接口细化，不声称上游 §10.1 已逐字列出这些路径。

L1 仅交付 OpenAPI、JSON Schema、静态验收断言和本 SPEC。L2 实现服务和 owner 内持久化；L3 执行故障注入及运行验收。本阶段只用已登记 Mock 凭证、对象引用、事件与受控状态查询；没有真实输入就不实现 ERP/PMC/MES/WMS 字段映射或真实 adapter。外部产品、版本、字段、原生表、单位及状态口径均待冻结，不通过示例暗示已确定。

P0 OpenAPI 与 11 个 schema、P1 OpenAPI 与 6 个 schema 原样保留。test_p15_contracts.py 锁定全部 19 个文件的原始字节 SHA-256，常量来自本次读取；禁止重新生成哈希、格式化旧文件或转换换行来掩盖变更。本交付不修改 gate.py、不重做 P0/P1 实现与验收。

交付新增文件：p15.openapi.json；p15-outbox、p15-inbox、p15-dlq、p15-receipt、p15-lifecycle、p15-event-api 六个 schema；test_p15_contracts.py；本 SPEC。前四个 schema 是记录，后两个是生命周期读取与传输容器。数据库记录结构是逻辑契约，不规定物理表名。

公共 Context 直接引用 common-context.json；新消息请求、记录与响应只在 context 下携带公共字段，禁止再平铺 tenant/factory/actor/trace 等副本。P0 EventEnvelope 是独立事实对象，仍保持 P0 的原有字段与 payload 结构，不改成新 Envelope。context.tenant_id、event.tenant_id 与可信身份必须一致；工厂、trace 和等级也须校验，不能通过嵌套伪造身份。引用解码、ACL 和等级真实性由可信服务验证，JSON Schema 不能比较任意两个字段。

GET 复用 P0/P1 的必需 X-Context JSON 头；这是既有传输方式，头不是认证，不新增 GET body。该头里的对象以公共 Context 格式传输；响应仍只嵌套 context。已有 P0/P1 的平铺结构不受本件改写。

## 2. 新增接口表

| 方法 | 路径 | 行为及成功响应 | owner / 运行单元 | 既有接口层 / 上游依据 |
| --- | --- | --- | --- | --- |
| GET | /internal/v1/tasks/{task_id} | 200 返回 TaskView，持久化 Task 状态、record_version、来源、更新时间与 Command 引用；核验 path.task_id=context.task_id | control / control-plane | L1 / §12、§13 |
| GET | /internal/v1/runs/{run_id} | 200 返回 RunView，持久化 Run 状态与版本；核验 Run 的 task 绑定及当前委托权限 | runtime / hermes-runtime | L2 / §12、§13 |
| POST | /internal/v1/events | 事实投递，持久化 inbox 后才 200；返回明确 disposition 和补拉/DLQ 位置，不执行业务动作 | 目标 consumer 的既有 owner / 下述八个运行单元各自本地端点 | L3 / §11 |
| GET | /internal/v1/events/dlq/{dlq_id} | 200 查询本 owner 死信原因、次数、人工状态、记录版本与原事件引用 | 原 outbox/inbox 所属 owner / 其既有运行单元 | L3 / §11 |
| POST | /internal/v1/events/dlq/{dlq_id}/replay | 命令：人工请求重放原事件；202 仅在重放请求、幂等记录和持久化队列提交后返回 | 原 outbox/inbox 所属 owner / 其既有运行单元 | L3 / §11 |
| POST | /internal/v1/commands/{command_id}/receipts | 事实：受限 adapter 提交权威凭证引用，Transaction 验证并决定 Command 终态；200 返回验证后记录 | transaction / transaction-service | L3 / §11、§12 |

owner-local 只表示同一协议分别部署在既有 owner 内，不是新服务、新 schema owner 或 L6。允许的运行单元是 security-gateway、control-plane、decision-service、hermes-runtime、manufacturing-core、tool-gateway、transaction-service、trajectory-eval。每个单元使用独立身份、迁移与 DB role，注册自身消费的事件种类和目标地址；不要求八个单元订阅全部事件。目标由可信服务路由与 ACL 选择，不接受 body 指定远程 owner，不建立集中事件服务代写所有 owner 的表。运行路由 manifest、订阅关系及审批运维岗位是 L2 必须提供的配置；具体部署值待冻结。

所有新增端点为 internal 受众，复用 P0 InternalIdentity，并核验用户委托范围。外部受众定义继续引用 P0，不让用户 bearer 被当成内部 broker/adapter 身份。事件投递限定登记 broker 或权威生产者；回执限定登记 adapter；DLQ 查询和重放限定本 owner 运维权限。跨租户拒绝与对象不存在的展示口径沿用 P0 的待冻结约束，不泄露存在性。

统一 Error 从 P0 复用。400/422 结构/参数错误，401/403 身份权限拒绝，409 幂等/版本/凭证冲突，429 预算，503 依赖不可用；404 生产业务语义与具体 Error.code 目录待冻结。未经验证或无法持久化时不得返回成功 ACK；200 的 ACK 仅证明接收持久化，不证明事实已应用或业务成功。202 只用于请求执行动作，不用于声明已发生事实。

DeliveryRequest.publication_evidence_ref 是生产者状态提交或权威凭证的受控证据引用。ReceiptSubmission 只含身份上下文、Command/原幂等键/payload_hash 和凭证引用，不接受调用者自报 outcome、verified、业务成功或过账字段。Transaction 在本域独立校验受限 adapter 身份及凭证绑定，再推导回执记录。仅设置布尔字段不构成凭证验证。

## 3. P1 缺陷①：单一真相源收敛

| 状态 | 唯一 owner 与保存位置 | 其他 owner 如何读 | 禁止的替代权威 |
| --- | --- | --- | --- |
| Task 编排状态、存在性及 Task record_version | control-plane 的 control 数据域，持久化且 tenant 隔离 | 本件 GET /internal/v1/tasks/{task_id}；外部仍用 P0 GET /api/v1/tasks/{task_id} | manufacturing-core 的 Task journal、内存缓存或 runtime 副本决定存在性/终态 |
| Run、Checkpoint、Memory 引用及 Run record_version | hermes-runtime 的 runtime 数据域 | 本件 GET /internal/v1/runs/{run_id}；创建/恢复仍用原 P0 接口 | control-plane 的 Run 展示投影成为可独立写入的运行事实 |
| Command、Saga、幂等及权威执行回执 | transaction-service 的 transaction 数据域 | 原 P0 GET /internal/v1/commands/{command_id}，需要时校验本件回执证据 | Task SUCCEEDED、Run COMPLETED、Tool 返回 accepted 或 broker ACK 代替执行事实 |
| 只读回答、知识 ACL 与行业事实投影 | manufacturing-core 的 manufacturing 数据域 | P1 既有只读接口，绑定经 Task owner 核验的任务及可信 Context | 另存一份 Task 状态来满足知识接口任务存在性 |

判断：Task 是 control 的权威编排记录，同时也是 Run/Command 的展示投影；投影含义不赋予它外部副作用的主责。Run 是 runtime 的运行事实；业务终态是 Transaction 依据源系统权威回执得出的执行事实。这三个对象不是同一状态枚举，不通过复制状态字段来统一。

L2 必须让所有 Task 写入经过 control owner、所有 Run/Checkpoint 写入经过 runtime owner。同一 owner 的独立进程/worker 通过该 owner API 或受限 owner 数据角色读取同一持久化库，不能依赖进程对象内存。manufacturing-core 核验知识任务时调用 control 的内部 Task 查询 API，携带可信 Context、截止时间及委托身份。control 不可用或读取超时返回 503/既有安全等待路径，不能以 journal、缓存或请求自报 task_id 判定存在。

P1 journal 可保留为回答/来源证据的受控存储载体，但须移除 Task 存在性和状态权威职责；若它仅承载重复 Task 状态，则在 L2 完成核对后退休该内部路径。不得在本阶段删除真实持久数据或凭空迁移冲突状态。已有冲突先报告并进入人工收敛；真实数据处理方案待冻结；不得用本 SPEC 当作删除真实记录的授权。L2 用运行依赖和权限证据证明旧权威读写路径退出，而非只改变量名。

control 的 Task 投影如需 Run/Command 更新，通过 owner API 查询并 CAS 更新自己的记录；Command 事件只能携带证据引用。禁止跨 owner 直接写表、join、外键，包括共用一个 PostgreSQL 集群时。ID、版本和 API/事件引用表达关联，不建跨库事务。内部 Task 查询只读 control，不反向依赖知识回答生成，避免读取存在性时产生循环流程。

控制台展示须区分编排/运行状态与执行状态，并附 status_source、updated_at。TaskView/RunView.is_posting_evidence 固定 false，business_execution_source 固定 transaction-service。副作用查询来自 Transaction；无法核验时标记未知或不可用，不能显示已过账。

## 4. outbox/inbox 事务边界表

| owner / 场景 | 必须同一 owner 数据库事务提交 | 明确不能共享事务的对象 | 提交、ACK 与恢复语义 |
| --- | --- | --- | --- |
| producer 发布平台状态事实 | 自身状态变化、版本 CAS、唯一 outbox、发布证据/审计意图引用 | broker ACK、其他 owner 投影/库、任何源系统库 | 提交前崩溃两者均无；提交后崩溃 outbox 保留等待投递 |
| dispatcher 发送 outbox | 更新自身投递次数、错误及租约位置；成功 ACK 后本地更新 SENT 与 ack_ref/sent_at | broker 的持久化接收 | broker ACK 与本地 SENT 之间崩溃可重发；不新增第二条 outbox |
| consumer 持久化入口 | 唯一 inbox RECEIVED、原 Envelope/发布证据及可恢复处理位置 | producer 库、broker ACK | 可以在入口事务提交后 200；尚未应用必须返回 RECEIVED；worker 重启可继续 |
| consumer 应用连续版本 | 投影、aggregate watermark、inbox APPLIED、需要派生的本 owner outbox/审计意图 | 其他 owner 的 Command/Task/业务表，源系统副作用 | 在锁/CAS 下原子应用；失败全部回滚，不能先标记 APPLIED |
| consumer 遇到缺版本 | inbox GAP、补拉队列/持久化工作项及缺失范围 | 源系统查询/网络补拉 | 不推进 watermark、不更新投影；补齐后重新走同一消费规则 |
| 本 owner 失败转 DLQ | 原 inbox/outbox 的失败位置、DLQ 原事件引用、原因/次数/人工状态与版本 | broker 或另一个 owner 的 DLQ | 失败记录自身也无法提交时不 ACK，保持可重试，不静默丢弃 |
| DLQ 重放请求 | 重放请求幂等记录、DLQ CAS/次数、原链路持久化重放工作项 | 目标 broker/源系统实际执行 | 202 只证明请求持久化；重放失败仍保留 DLQ 历史 |
| transaction 收敛回执 | 去重回执、持久 Command 终态/CAS、关联对账位置、command.succeeded 等 outbox | adapter/源系统的原生操作事务、Tool owner 库 | 相同回执重复安全；冲突凭证 fail-closed/人工，不能覆盖成功事实 |
| runtime 检查点 | Run/Checkpoint 版本、程序位置、命令与已完成回执引用、租约/fencing 检查及需要的 outbox | Transaction 已执行命令、模型调用或其他 owner 库 | 恢复先查询既有 Command，再继续；旧 worker 不得提交 |

入口 inbox RECEIVED 的预持久化不等于“投影与去重拆开提交”：真正表示已应用的 APPLIED 标记、投影和 watermark 必须同事务。RECEIVED/GAP/DLQ 是待处理位置，不能被用作“event_id 已出现，所以永久跳过”的 consumed 条件。重复入口只能复用同一逻辑 inbox 记录；尝试历史可追加在该 owner 内，不能增加第二个已应用标记。

outbox 的逻辑唯一键为 context.tenant_id + event.event_id；inbox 同样按 tenant + event_id 唯一，但作用域是每个 consumer owner。多 worker 和并发插入必须由持久唯一约束与锁/CAS 收敛，不能用内存 set。发布者须验证 event_id 的不可变绑定：tenant、aggregate、版本、事件类型、payload_hash、发布证据及事实发生时间。同 ID 不同内容是冲突，不按重复忽略。接收时间可在入口记录 received_at 单独保存，不能因此改写原 Envelope 身份或 payload。

## 5. 事件目录与一致性规则表

Envelope 必填项、UTC 格式、14 类 enum 和 MinimalPayload 完全引用 P0 event-envelope.json；不在 P1.5 定义另一个版本。事件正文只允许 P0 payload.payload_ref / payload.payload_hash，不扩展任意 payload。敏感正文、密钥及原始回执进入受 ACL/等级保护的本域对象存储；引用与哈希也须按 tenant/用途保护。C3/C4 事件不能发送到云 broker，不能因只有引用就绕过数据域限制。

下表是发布证据职责目录，不是外部字段映射；P1.5 仅验证登记 Mock 来源。

| run.waiting_approval | runtime / hermes-runtime | 已持久 Run 等待/检查点 |

| 规则 | 可执行语义 | 失败/恢复路径 |
| --- | --- | --- |
| 投递 | 至少一次；不承诺全局 exactly-once。broker 持久 ACK 后才 SENT | ACK 后未 SENT 可重复投递；同 outbox 更新 attempt_count |
| 去重 | 每 consumer 的 tenant+event_id 唯一；APPLIED 重复到达返回 DUPLICATE，不再应用/发副作用 | 同 ID 不同不可变内容 409/DLQ；保留诊断，不能当正常重复 |
| 排序 | 按 P0 aggregate_key：tenant_id+aggregate_id，watermark 持久化且单调 | aggregate_id 在同 tenant 内须跨 aggregate_type 唯一；冲突 fail-closed，不按时间戳比较 |
| 初始化 | Mock 连续版本流从 0 开始，未应用 watermark=-1；已有可信基线 B 时只允许 B+1 | 首条事件不可直接设 watermark=version-1；高起点须补拉或验证权威基线 |
| 连续版本 | 未应用 event_id 且 version=watermark+1，锁/CAS 成功才 APPLIED | 投影、inbox、watermark 和派生 outbox 同事务；after=event.version |
| 迟到 | version 小于 watermark：LATE，不写投影、不降 watermark，保留处理证据 | 对已应用相同 event_id 优先返回 DUPLICATE，不能重新执行动作 |
| 同版本冲突 | 未应用 event_id 且 version=watermark：DLQ | 不以晚到时间或 event_id 排序覆盖；需要权威核验/人工 |
| 缺版本 | version 大于 watermark+1：GAP，持久补拉工作项，投影不变 | 补齐后按版本逐条应用；超出恢复预算进入 DLQ/人工，禁止跳过 |
| 缺字段 | Envelope 缺 aggregate_version 是结构错误，422 且不得 ACK | 不推断时间戳为版本；保留可诊断拒绝；这与“缺中间版本”不同 |
| DLQ | 错误使用统一脱敏 Error，保留次数、原事件、证据和人工状态 | 失败记录写不入库不 ACK；阈值/时间预算待冻结，不无限重试 |
| 重放 | 原 event_id/tenant/aggregate_version/payload_hash/发布证据不变，走原去重与排序 | INBOX 回到原 consumer；OUTBOX 回到原 producer 原投递记录，broker ACK 后 SENT |
| 并发 | 唯一约束 + tenant/aggregate 锁或 CAS，dispatcher/worker 租约与 fencing | 旧 worker 写入拒绝，不能覆盖新 watermark 或发布第二事实 |
| 派生动作 | 事实消费只更新投影或发出受控请求；写命令仍经原 Tool/Transaction/Policy/Approval | inbox.side_effect_emitted 固定 false；派生本地 outbox 不是外部执行许可 |
| 删除/更正 | 按权威版本事实及保留规则追加传递，历史轨迹不静默改写 | 首期目录不能表达的新增事件类型/负载版本待冻结，不编造第 15 类 |

版本比较使用数值而非字符串或 occurred_at。record_version 是记录 CAS 版本，aggregate_version 是事实流版本，两者不可混用。上游没有规定所有外部源版本连续或从 0 开始：Mock 的连续序列是本阶段测试基线，生产版本归一化、游标与快照证据协议待冻结。禁止把不连续原生版本直接套成连续事件序列；无法证明缺口已恢复时进入补拉或人工。

DLQ 状态 OPEN / REPLAY_QUEUED / RESOLVED / MANUAL_REVIEW 是队列人工处置状态，不扩展 P0 Task/Run/Command 生命周期。RESOLVED 须有处置人、原因和证据；只表示死信处理收敛，不表示业务执行成功。OUTBOX 重放复用原 outbox/event_id；INBOX 重放不能插入第二条 inbox，不得将 GAP/DLQ 视作已应用。关闭或重放不得删除诊断与尝试历史。

## 6. 回执、UNKNOWN 与恢复

| 观察/回执 | Command 与展示语义 | 允许的下一步 |
| --- | --- | --- |
| accepted / HTTP 202 | 请求已受理；business_success=false；posting_status 只能 NOT_CONFIRMED/NOT_APPLICABLE | 查原 Command 状态，不能宣称过账，也不能另造成功事件 |
| UNKNOWN / 超时 / 回执丢失 | 保持 UNKNOWN，必要时 MANUAL_REVIEW；不可表述成功或 FAILED | 先查源系统权威执行状态；无法查询则人工，不盲目重试/补偿 |
| 已核验 SUCCEEDED 回执 | Command SUCCEEDED，business_success=true；绑定 tenant/command/原键/hash/source/version | 持久回执与 Command/outbox 后发布 command.succeeded |
| SUCCEEDED 但没有过账凭证 | 可以是其他业务动作成功；不得显示 POSTED | 过账口径和凭证待冻结；NOT_APPLICABLE/NOT_CONFIRMED 明确展示 |
| 已核验过账凭证 | SUCCEEDED 且有 posting_evidence_ref 才能 POSTED | 源系统是否确已过账由 adapter 的冻结口径验证，字段不自证 |
| 已核验 FAILED 回执 | Command FAILED、business_success=false；保留权威失败证据 | 按既有策略/批准决定后续，不能用 HTTP 5xx 合成此回执 |
| 已核验 NOT_EXECUTED 查询证据 | UNKNOWN/MANUAL_REVIEW 的恢复依据，仍不算成功 | 仅用原幂等键和相同 payload 重试，并重新校验权限/批准/对象版本 |

回执内容绑定 tenant、command_id、原 idempotency_key、canonical command_payload_hash、source_system 与受控凭证内 source_version。引用的原文必须通过来源身份/签名或等价权威查询验证，源版本从凭证读取；真实验证机制待冻结，Mock 用登记可验证证据代替。不能以“adapter 发来了”或 authority_verified=true 跳过验证。相同 receipt_id+相同证据返回原结果；相同 ID 不同凭证 409；不同 ID 的冲突终态进入人工收敛，不能以迟到 accepted/UNKNOWN 降级已核验 SUCCEEDED。

Task/Run 的成功状态没有过账证明效力。Cancel 只能停止尚未开始步骤；在途/已完成 Command 必须核验及适用补偿，Task CANCELLED 不表示源系统回滚。恢复仍复用 P0 Checkpoint 与 RunResumeRequest，保留程序位置、上下文引用、待确认 Command、已完成回执以及模型/策略版本；先逐个查询原 Command，再继续。检查点 CAS 和租约 fencing 拒绝旧 worker；已成功步骤不重执行，UNKNOWN 步骤阻塞继续或进入人工。

## 8. L3 运行验收断言表

故障注入只针对登记 Mock 与可恢复测试存储。观测分为 owner API 返回、owner 自身存储证据、Mock 执行次数和无正文审计/指标。L3 不通过跨 owner join 验收；分别读取 owner 导出的受限证据，再按 tenant/trace/事件引用比对。不能仅依据日志一句“成功”或单次 HTTP 200 判绿。

| 场景 | 故障注入方式 | 可观察断言 |
| --- | --- | --- |
| 生产者崩溃 | 在状态写入后、事务提交前终止 producer；另一次在提交后、broker 投递前终止；重启同 owner | 状态与 outbox 要么都提交、要么都没有；不存在“状态已改但事件丢失”；提交后重启仍可投递且 outbox 同一逻辑 event_id 只有一条 |
| 重复投递 | broker 确认后截断本地 SENT 更新；重启重发相同 event_id；并发重复至少两次 | 同 event_id 重复到达：投影只应用一次，inbox 有去重记录，不产生重复副作用；watermark 不重复推进；重复返回 DUPLICATE；同 ID 不同 hash 进入冲突/DLQ |
| 乱序到达 | 对 watermark=3 的 Mock 流先送 version=5，再送迟到 version=2，最后补 version=4 | 迟到事件不覆盖新事实；缺版本进补拉队列，不直接应用；5 到达时投影和 watermark 保持 3，2 只记 LATE；补 4 后按 4、5 收敛；tenant/aggregate 各自独立 |
| 投递失败 | 注入 broker 发送失败或 consumer 投影事务失败直到配置预算耗尽；人工请求重放，随后再投同一 event_id | 进入 DLQ 并保留原因与次数；重放后仍走原去重规则；失败期间无 SENT/APPLIED 假标记；重放请求重复不新增动作；DLQ 历史保留，GAP/DLQ 不被永久当作 consumed |
| 回执缺失 | Mock 执行动作后丢弃回执并注入超时；另组让 Mock 证明原请求未执行，再恢复查询 | 命令保持 UNKNOWN；查询源系统确认未执行才用原幂等键重试；绝不换键；已经执行组通过原状态查询收敛，Mock 执行计数不增加；查询不可用组仍 UNKNOWN/人工 |
| accepted 语义 | 返回 accepted、延迟权威回执、再注入 UNKNOWN；随后提交可验证成功回执；另组给 SUCCEEDED 但无过账证据 | accepted / UNKNOWN 绝不显示“已过账”；只有权威回执驱动成功；Task SUCCEEDED/Run COMPLETED 和 HTTP ACK 不能替代过账证据；无 posting_evidence_ref 的成功动作不显示 POSTED |
| 单一真相源 | 在 control 进程受理 Task，由独立 manufacturing 进程做 P1 知识问答；重启 control/runtime；阻断 control；伪造旧 journal 的矛盾状态 | Task/Run 状态在跨进程读写下一致；不存在两个互相矛盾的真相源；知识链经 control API 查询存在性；重启保留状态；control 不可用时 fail-closed/503，不从 journal 宣称任务存在 |
| consumer 崩溃 | 在投影写入后、inbox APPLIED 提交前终止；另组在入口 RECEIVED ACK 后终止 | 投影/watermark/APPLIED 同回滚或同提交；入口已 ACK 的 RECEIVED 工作重启可继续；不会丢失或重复应用 |
| 同版本/同 ID 冲突 | 不同 event_id 携带同 tenant+aggregate+version；同 event_id 替换 hash 或发布证据 | 新事实不被覆盖；显式 409/DLQ/人工；无成功 ACK 掩盖冲突；错误可追溯到原事件 |
| 回执伪造与乱序 | 普通服务提交回执；登记 adapter 提交不匹配 tenant/command/key/hash 的证据；成功后补送 accepted | 未授权/不匹配凭证拒绝；回执/Command/outbox 无部分推进；成功不被迟到 accepted 降级；冲突终态进入人工且历史证据保留 |
| 并发恢复/旧 worker | 两个 worker 竞争同 Checkpoint CAS；租约过期后让旧 fencing token 提交；已成功步骤再恢复 | 只有当前租约/CAS 获胜者推进；旧 worker 拒绝；先查原 Command；已成功步骤 Mock 执行计数不增加 |
| 取消在途 Command | 命令处于 EXECUTING 时取消 Task，随后 Mock 回执成功 | Task CANCELLED 不被展示为动作已撤销；原 Command 回执仍可查询；补偿按适用策略/人工处理，不凭取消重复或反向执行 |
| ACK/失败记录不可持久化 | 注入 inbox 入口提交失败、DLQ 提交失败或重放队列提交失败 | 不返回 durable=true 的 200 或 accepted 的 202；上游保留重试位置；无静默丢弃、伪成功或不可恢复的已 ACK 消息 |
| 跨 owner/租户隔离 | 用 manufacturing DB role 写 control/runtime 或建立跨 owner join/FK；用不匹配 Context 读 Task/DLQ/凭证 | owner 数据权限拒绝；无跨 owner 写表/join/FK；tenant 不匹配 fail-closed 且不泄露存在性；broker/引用 ACL 同样隔离 |
| 敏感正文 | 在 P0 payload 增加原文键，或将 C3/C4 消息路由到云 broker | Schema/治理拒绝；事件、DLQ 错误与日志没有敏感正文；引用也经过批准数据域与租户 ACL |

每项证据记录注入点、配置预算、UTC 时间、tenant/trace、原 event_id/Command/幂等键引用、owner API 前后结果、各 owner 的唯一性/事务提交证据和 Mock 执行计数。L2 给出可控 failpoint 或测试 harness；L3 负责运行和报告，不能在生产服务开放任意故障注入接口。

静态门禁仅只读 packages/contracts；它验证 19 项字节锁定、新接口/认证/Error/Context、P0 事件目录与 Envelope 引用、记录封闭性及正反实例、事务/去重/版本/DLQ 声明和 A14 对齐的 accepted/UNKNOWN 限制。有限版本决策表解释器只是检查声明，不模拟数据库或证明运行效果。本次按授权只写文件，没有执行门禁或运行验收，不宣称已跑绿。
