## 0. 先给结论

1. **V3.0 不是给 V2.1 加功能，是换架构底座。** 上游文档要求「一数一源、决策与执行分离、工具受控、事务可恢复、轨迹可验证」，而 V2.1 是一个 158 path 的单体、37 张表挤在单 schema、靠应用层 `WHERE company_id` 隔离、没有任何 Command/幂等/Saga 抽象。这不是补丁能补的差距。
2. **但 V3.0 能安全地与 V2.1 并存。** P0（契约与骨架）与既有 `backend/` 零交集，风险为零；真正需要设计的是 P1 之后「新老数据流在哪收口」。
3. **最高杠杆点不是写代码，是先把契约冻住。** 上游文档 §16 明确 P0 就是契约与骨架，且「对未填项实现显式配置和 Mock」。契约错一次，后面 8 个服务全返工；契约对了，L2/L4 可以并行铺量。
4. **本仓库另有两个与升级无关、但优先级更高的隐患**（详见 §6）：生产库明文口令已进 git 历史并推到 prod 远程；部署包内含客户营业执照原件。**建议先于升级处理，或至少并行处理。**

**当前承诺的执行范围**：只做 P0（契约 + 骨架 + 契约门禁），产出可 `exit 0` 的门禁证据，不碰 `backend/` 任何代码、不部署。

## 1. 目标态（V3.0 摘要，只列可执行约束）

### 1.1 五大 Plane

| Plane | 核心组成 | 边界 |
| --- | --- | --- |
| 接入与安全面 | Web/HMI、OpenClaw 渠道、Security Gateway、Model Router | 认证、租户、数据等级、出域、模型入口与输出治理 |
| 员工控制面 | Employee Registry、Task API、配置/版本、Policy、Approval | 定义员工能力与风险范围，管理任务与批准权 |
| 智能运行面 | Rules、Jev Decision Fabric、Hermes Runtime、Human Queue | 分流/分析/长任务/人工接管；**不取得执行授权** |
| 制造能力与执行面 | Manufacturing Harness、Tool Gateway、Transaction、Adapters、Edge | 行业语义、受控工具、跨系统事务、现场边缘执行 |
| 轨迹与评测面 | Trajectory、Audit、Eval、Release Registry | 可追溯证据、效果评估、模型与策略晋级/回滚 |

**两条治理轴不可混同**：Security Gateway 管「数据能否出域」，Business Control 管「副作用能否发生」。允许发模型请求 ≠ 允许改订单。

### 1.2 八个运行单元（首期）

`security-gateway` / `control-plane` / `decision-service` / `hermes-runtime` / `manufacturing-core` / `tool-gateway` / `transaction-service` / `trajectory-eval`。
其中 control-plane 内多逻辑模块、manufacturing-core 内多领域模块**首期合并部署，但代码与数据库所有权不合并**。

### 1.3 硬契约（违反即返工）

| 契约 | 内容 |
| --- | --- |
| 接口分层 | L0 `/api/v1/**` 用户 API；L1 控制 API；L2 `/internal/v1/**` 智能 API；L3 行业与执行 API；L4 系统 adapter；L5 `/edge/v1/**` 现场 API（**不开放到公网**） |
| 数据分级 | C0 公开 / C1 内部一般 / C2 敏感业务 / C3 商业机密（**仅本地模型**）/ C4 核心机密（**仅本地 + 任务白名单，密钥不得进上下文**）；未知等级默认禁止出域；合并上下文按最高等级 |
| 模型治理顺序 | 身份租户校验 → 访问范围 → 输入分类 → 最小化脱敏 → DLP/出域 → 模型白名单 → 调用 → 输出 Schema/泄露扫描 → 本地 Token 恢复 → 消费 → 分级审计 |

| 存储所有权 | 每服务独立 schema + 独立 DB role；**严禁跨 owner 直接写表、跨服务 join、跨 owner 外键**；跨边界用 ID + API/事件引用；所有业务主键/唯一索引/幂等域**包含 tenant** |
| 状态机 | Task / Run / Command / Saga / Edge release 五条，上游 §12 已给全 |

## 3. 开工结构决策（ADR-001，已定）

**决策**：V3.0 的 8 个运行单元建在**新目录 `services/`**，契约在 `packages/contracts/`，与既有 `backend/` 并存。

**理由**：
1. 既有 `backend/` 在产（有真实客户数据、计费开票），一次性重构会制造不可控的生产风险。
2. 契约优先的架构要求先立契约再迁实现，并行目录是唯一不阻塞的顺序。
3. 迁移按**能力对齐**增量进行（RAG / 渠道 / 行业包 → manufacturing-core 与 integrations），每步都可独立验收与回滚。

**替代方案与否决理由**：
- 直接在 `backend/` 内原地改造 → 否决：86 个 router 无版本化路径，改造期间无法灰度。
- 另开新仓库 → 否决：契约与实现会漂移，且本仓库已有同步/部署链路。

**触发重新评估的条件**：① 上游要求从零代码库重建；② V2.1 计划停服；③ `services/` 与 `backend/` 出现必须共享数据库事务的场景（当前设计禁止跨 owner 事务，应不出现）。
