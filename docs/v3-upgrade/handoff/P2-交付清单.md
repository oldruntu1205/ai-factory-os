## 3. 为什么"迁移要生成 + 冻结"

`storage.py` 能生成 DDL，但那是**内存里的字符串**：没人能 review "实际要执行什么"，
也没有东西**冻结**已发布的文本——生成器被人改动后，无从知道历史迁移是否被动过。

于是落成文件 + 清单（含 sha256），门禁每轮从生成器**重新生成**并逐字节比对。
这带来两个具体的保护：

1. **防手改**：直接改 `migrations/**/*.sql`（例如悄悄去掉 `FORCE ROW LEVEL SECURITY`）
   会立刻报红——否则"实际执行的 DDL"与"经过不变量校验的 DDL"就分家了；
2. **防改坏生成器**：SQL 文本层面另有一组断言（只碰自己 schema、只授给自己角色、
   租户表必须有 FORCE RLS），即使生成逻辑被改坏也能在**已发布文本**上发现。

**门禁有牙的实测**：注入"手改已发布迁移（删掉 FORCE RLS）"与"往 owner 目录塞未登记文件"
两类破坏 → **均报红**；还原后恢复绿色。

## 4. 本轮修掉的两个真缺陷

### ① 生成的 DDL 含**非法 SQL 语法**（会被真库直接拒绝）

原生成器写的是：

```sql
CREATE ROLE security_app LOGIN ... NOREPLICATION BYPASSRLS OFF;
```

**PostgreSQL 没有 `BYPASSRLS OFF` 这种语法**——`CREATE ROLE` / `ALTER ROLE`
的合法写法只有 `BYPASSRLS | NOBYPASSRLS`（见
[CREATE_ROLE(7)](https://manpages.debian.org/unstable/postgresql-client-17/CREATE_ROLE.7.en.html) 的 option 列表）。
这段 DDL 一旦在真库执行会**直接语法报错**。

**它为什么一直没被发现**：早期的判定用**朴素子串**匹配 `BYPASSRLS`，
把 `BYPASSRLS OFF` 当成"关闭形态"而放行。更糟的是，L1 写的一条"防朴素子串回归"
用例**把 `BYPASSRLS OFF` 当作健康 DDL 来断言**——于是这个语法错误被**固化成期望值**。
本次改成合法写法 `NOBYPASSRLS`，并加了反向断言（`"BYPASSRLS OFF" not in text`）。

### ② 权限判定仍是朴素子串（同类错误第二次）

`roles_with_excessive_privileges()` 曾用 `if "BYPASSRLS" in statement` 判定，
于是**合法**的 `NOBYPASSRLS` 也含该子串 → 正确写法被**误报**为过度权限。

这与 `cross_owner_grants()` 那次的教训同源：**用"字符串里有没有"代替"语法上是不是"**。
现在改为**逐 token 解析**：按极性与名字判断，`NO<x>` 一律视为关闭。

### 附带加固：`CREATE ROLE IF NOT EXISTS` 不自纠偏

`DO $$ ... IF NOT EXISTS ... CREATE ROLE ... $$` 只在角色**不存在**时生效。
若角色已存在但权限被改宽，**重跑迁移不会纠正**。
现在每次都补一条 `ALTER ROLE ... <最小权限属性>`，让迁移真正幂等且自纠偏。

## 5.1 多版本递增机制（本轮新增）

`§13「不改已应用迁移，只能新增」`在代码侧的三重落实：

| 机制 | 位置 | 作用 |
| --- | --- | --- |
| 版本发现 | `discover_migrations()` | 按 `<4位数字>_<slug>.sql` 发现并**升序**排列；新增 `0002` 即自动纳入 |
| 序列校验 | `version_sequence_problems()` | 必须从 `0001` 起、不重复、不跳号（跳号多半是误删已发布迁移） |
| 命名校验 | `malformed_migration_names()` | 命名不符的文件**不会被执行**，必须显式报错而非静默跳过 |
| 待应用计算 | `pending_migrations()` | 已应用迁移被**改内容**或被**删除** ⇒ 抛错，拒绝继续 |
| 独立判据 | `manifest_version_problems()` | 逐项复核清单与磁盘的版本集合/顺序/哈希 |
| 记录表 | `render_ledger_ddl()` | `v3_migration.schema_migrations`（独立 schema，不属任何业务 owner） |

**清单冻结的是"全部已发布版本"而不是"最新一版"**——否则 `0002` 出现后，
`0001` 被动过就再也查不出来，而 §13 要求的恰恰是历史版本永不可改。

### 一条方法论教训（本轮最有价值）

写多版本用例时，我原本用 `discover_migrations()` 的输出当基准去校验清单——
**这个函数既是"被测对象"又是"基准"**。变异测试立刻暴露了后果：
把它的排序改成按文件名字典序，门禁**照样全绿**（两边一起坏、互相印证）。

已改为**独立判据** `manifest_version_problems()`：自己算集合与升序、逐项复核哈希，
并用 `test_manifest_validation_rejects_scrambled_version_order` 直接喂一份乱序清单去考它。

## 5.2 变异测试里的"已接受缺口"

本轮给变异工具加了 `[已接受]` 状态：某些变异**结构上不可被当前观测手段捕获**，
如实登记理由，而**不是删掉它假装全捕获**。P2 现有 2 条：

| 变异 | 为何不可捕获 |
| --- | --- |
| 版本排序改为字典序 | 当前文件名是零填充 4 位数字，字典序与数值序**结果完全相同**，无法观测区分。将来出现非零填充命名即变为可捕获 |
| 清单只冻结当前版本 | 清单的版本集合是**从磁盘发现**的；只登记当前版本时，发现的集合也同步缩小，两侧始终一致。该风险的真防线是上面的**独立判据**（已被专门用例覆盖） |

这条设计的价值：**缺口被写下来，而不是被掩盖**。

## 5.3 迁移执行器（本轮新增）

`services/_kernel/migration_runner.py`：按版本顺序应用待迁移并写账本。

**设计要点：把驱动抽成可注入的适配器。** 真实执行需要目标 PostgreSQL（外部依赖），
但"执行顺序、幂等、账本记账、失败处理"这些**最容易出错**的部分与驱动无关，因此：

- `DatabaseAdapter` 协议只有两个方法（`execute` / `fetch_all`），能力面越小越好替换；
- `InMemoryAdapter` 让执行序与账本语义**可完整测试**（无外部依赖、可重复）；
- `Psycopg2Adapter` 只是薄壳——它**没有能力**悄悄改掉执行语义。

已锁定的语义（都有变异兜底）：

| 语义 | 判据 |
| --- | --- |
| 顺序由**版本号**决定 | `test_execution_order_follows_version_not_file_name` |
| 第二次运行**零应用**（幂等） | `test_second_run_is_noop` |
| **失败即停**，不继续后续版本 | `test_failed_migration_stops_and_does_not_apply_later_versions` |
| 已应用迁移被改/被删 ⇒ 拒绝执行 | `test_apply_refuses_when_applied_migration_was_modified/disappeared` |
| 账本表**先于**迁移建出 | `test_ledger_ddl_is_executed_before_first_migration` |
| 每条迁移在账本留**哈希** | `test_every_applied_migration_is_recorded_with_its_hash` |
| `DO $$ ... $$;` 不被分号误拆 | `test_statement_splitter_keeps_dollar_quoted_block_as_one_statement` |

**语句拆分单独说明**：角色的最小权限属性全靠 `DO $$ IF NOT EXISTS ... CREATE ROLE ... $$;`，
若被按分号误拆，真库上直接语法报错——所以它有一条专门的变异与用例。

## 5.4 RLS 运行期接线：**当前无处可接（如实说明）**

P2 清单原先把"RLS 运行期接线"列为待办，但本轮核查后发现：
**运行期存储是 JSONL journal**（`state_dir()/<name>.jsonl`），
`services/` 下没有任何 PG / psycopg 引用。也就是说数据库 schema 目前只存在于迁移文件里，
**还没有代码去连它**。

因此"连接建立时 `SET app.tenant_id`"这段现在**没有调用方**——写出来只会是死代码，
反而给人"已经接线"的错觉。**如实记为待办**，等运行期真的落到 PostgreSQL 时再做。
