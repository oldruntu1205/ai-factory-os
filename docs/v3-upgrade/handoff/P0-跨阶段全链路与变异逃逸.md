# 跨阶段全链路 + 一次"变异逃逸"暴露的测试缺口

- 日期：2026-10-05
- 依据：上游 §6 全链路一致性；§17 A14「UI/API 状态契约验证」
- 判据：`scripts/gate.py --stages p0,p1,p15,p2,p3,p4,assertions` **exit 0**（1277 用例）；
  变异 **124 个可捕获项全捕获**

---

## 一、为什么前 23 轮之后还要做这个

前 23 轮把每一**环**都测了：路由可达、契约合规、入参健壮、Guard 语义、
审批不可改判、回执驱动成功、后台显示口径……

**但没有一条测试把整链连起来。**

这不是形式主义。本项目已反复证明**交接点**才是缺陷高发处：

| 曾经的缺陷 | 为什么单环测试抓不到 |
| --- | --- |
| 一条接口已接线却**零覆盖** | 各环都绿，只是那条没人调 |
| `GET /internal/v1/commands/{id}` 对 P3 命令**直接 500** | 可达性测试用占位 id，走到 404 就返回 |
| 任务↔命令**全仓无写入路径** | 各环都合规，缺的是环之间的关联 |

所以本轮的价值不在"再测一遍各环"，而在**让交接点显式接受断言**：
每个交接点要么被证明可用，要么被如实记为已知缺口——**不允许"没人看"**。

## 二、7 条用例覆盖的交接点

| 用例 | 交接点 | 断言 |
| --- | --- | --- |
| step1 | 外部系统 → 事件受理 | **受理不得声称业务成功**（`business_success` 固定 false） |
| step2 | 任务创建 → 读取 | 编排状态必须带**来源与更新时间** |
| step3 | 批准 → 命令 | 绑定 payload 哈希；**已成立不可改判**（409） |
| step4 | 命令 → 执行 → 回执 | 权威回执驱动 `business_success=true` |
| step5 | 回执 → **过账结论** | **`posting_status` 必须仍是 `NOT_CONFIRMED`** |
| step5b | 回执 → **控制台数据源** | 控制台读的接口必须报出同一批事实 |
| step6 | 链路事实 → **界面结论** | 用 node 真跑 `status.js`，界面必须显示"未过账" |

**step6 是跨语言的**：链路的断言在 Python，后台的判定在 JS，
两者此前**从未在同一处交汇**。这一跳用 `node --input-type=module -e` 真的调用
`apps/web-admin/src/status.js`，而不是在 Python 里重写一遍口径——
重写等于又造第二套真相，而"两套口径分叉"正是本项目反复吃亏的地方。

## 三、⚠️ 一次真实的"变异逃逸"——本轮最有价值的发现

加完整链用例后，我按惯例加了 4 条变异。结果：

```
[逃逸] 全链：过账状态被写死为 POSTED          ← 门禁仍然通过
[逃逸] 全链：权威回执不再驱动业务成功          ← 门禁仍然通过
[捕获] 全链：已成立的批准可被改判
[逃逸] 全链：命令权威视图的 status 被写死为 accepted  ← 门禁仍然通过
```

**三条逃逸。** 排查后根因很实在：

> 我的全链用例断言的是 **`_reconcile` 的响应**，
> 而这三处字段在 **`_p3_command_view`** 里 ——
> **全链用例从未调用 `_p3_command_view`。**

而 `_p3_command_view` **正是管理后台读的那个接口**
（`GET /internal/v1/commands/{id}/execution-record`）。

也就是说：**链路验的是"库里的账"，界面读的是"另一个视图"，
两者从未在同一处对上** —— 而"接口说成功、界面显示成功"这类事故，
恰好就藏在这个缝里。

**这正是我写这条全链用例的初衷（防交接点缺陷），而它自己就犯了同一个错。**

### 修法：补 step5b

新增 `test_chain_step5b_console_data_source_reports_the_same_facts`——
走完整链之后，**从控制台的数据源再读一次**，断言：

1. 权威回执在视图里**可见**（否则界面无从判断过账）；
2. `business_success` 与链路一致（写死 `False` 被抓）；
3. **`posting_status` 必须是 `NOT_CONFIRMED`**（写死 `POSTED` 被抓）；
4. `status` 是执行侧终态、`status_source` 是执行侧（写死 `"accepted"` 被抓）。

补完后 4 条变异**全部被捕获**。

> **这条经验比用例本身更值钱**：
> 写了一条"防交接点缺陷"的用例，不等于它真的覆盖了交接点。
> **只有变异能告诉你它覆盖了没有。**

## 四、一处如实登记的缺口：任务 ↔ 命令

`command_refs` 只在任务创建时被置为 `[]`，**全仓没有任何代码路径写入它**
（事件链路处理的是事件投影，不填这个字段）。
命令记录**自己**带 `task_id`——那一半是通的；缺的是任务侧的索引。

**后果很具体**：
- 没有 API 路径能从任务走到它的命令，所以管理后台只能**并列查询、不能下钻**；
- 审计时无法从任务定位到它产生的副作用。

处理方式：写成一条**缺口登记用例**（`test_chain_gap_task_command_link.py`）。
一旦关联被接上，它会立刻报红并提醒更新——
而不是让缺口静默地"看起来已经实现了"。

这比"断言 `command_refs` 为空"更准确：**前者描述现状，后者会把缺陷固化成期望**。

该文件按**文件级豁免**登记（`UNTAGGED_SUITES`），理由是：
上游 A01–A14 里**没有任何一条**覆盖"任务与命令的索引"，
硬塞一条相近的断言会稀释它的含义。

## 五、判据核对：为什么它不属于 A14

| 断言 | 原文 |
| --- | --- |
| A14 | 任务成功只由权威执行回执驱动，accepted/未知不显示已过账 · **UI/API 状态契约验证** |

A14 讲的是"**状态**契约"（什么能显示成功），不是"**索引**是否存在"。
所以缺口用例不挂 A14，而是登记豁免——**归属要核对，不能"看着像"就挂上去**。
（本项目已犯过一次：跨租户用例错标成 A09，实际属 A01。）

## 六、已知限制

1. **step3 是缺口而非期望**：它断言的是现状。接上关联后必须改。
2. **step6 依赖 node**：无 node 时直接返回（由 `tests/web_admin` 明确 skip 并说明，
   **不算通过**）。
3. **只覆盖一条主链**：Saga 补偿链、取消链、断连补报链**未做全链**——
   它们各自有单环测试，但没有跨阶段串联。
4. **全链跑在 mock 身份下**：真实 SSO 接入后需重跑（见 ADR-0004）。
5. `_p3_command_view` 的 `status` 断言依赖 `"status": record["status"]` 这一行
   在文件中**唯一**（它靠 `approval_ref` 那行配对锚定）——
   若该行被重构，变异会报"无效"而不是"逃逸"，提醒定位。
