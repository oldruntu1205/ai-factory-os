# 员工与岗位授权数据模型（契约）：把「缺数据」变成有形状的东西

- 日期：2026-10-05
- 依据：上游 §6（岗位 ACL）、§7（R1 限额 / R3 岗位批准与职责分离）、§10.1（管理权与批准权分开）、§15（员工页）
- 判据：`scripts/gate.py --stages p0,p1,p15,p2,p3,p4,assertions` **exit 0**（1369 用例）

---

## 一、上一轮我确认了「缺的不是路由，是数据模型」

`registry.mock.json` 每租户只有 `employees: ["employee-planning"]`（**裸 ID**）。
所以员工页做不出来，`position_authorized` 与 `within_limit` 两项批准检查**只能记 `UNKNOWN`**。

本轮把那个数据模型**建出来**——但**不填数据**（模型 ≠ 数据，
`test_data_gap_register.py` 继续断言登记表里数据仍未到位）。

## 二、模型不是我发明的：逐条对上游

| 上游原话 | 落到哪个字段 |
| --- | --- |
| 「RAG 在检索前过滤 tenant/工厂/**岗位** ACL」 | `positions[].delegated_scopes` |
| 「R1 …明确工具白名单和**限额**」；「R3 …明确**岗位批准**、职责分离」 | `positions[].limits[]`（按 `RiskClass`） |
| 「配置版本化，**管理权与业务批准权分开**」 | `config_authority` |

**关键设计判断：限额挂在「岗位」上，不挂在「人」上。**

上游三处都写「岗位批准」「岗位 ACL」，**没有一处写「某人可批多少」**。
所以员工的权限 = 其所任岗位的并集。改权限靠**改任命**，不靠逐人配额度——
否则职责分离会退化成一份越来越难核对的个例清单。

## 三、⚠️ 契约门抓到我的三处真错误（都改了，不是改测试）

### ① `$ref` 旁边写了 `description`（3 处）

JSON Schema 里 **`$ref` 的 sibling 会被忽略**——那些说明文字看着像注释，**实际会被静默丢弃**。
契约门拒绝这种写法。**这是真缺陷**：写的人以为留下了说明，读的人什么也看不到。

### ② 我让对象内部带了 `tenant_id` / `actor_id`

契约门明确拒绝闭包对象出现这三个字段（`tenant_id` / `actor_id` / `trace_id`），
理由是**它们属 Context**；允许出现会让人以为租户归属可以随对象走。

- `EmployeeRecord.tenant_id` → **删掉**。`EmployeeRegistry` 已是每租户文档，
  记录级再带一次是冗余。
- `EmployeeRegistry.tenant_id` → **也删掉**。租户归属由**请求的 Context** 提供，
  本仓一律如此。
- `EmployeeRecord.actor_id` → **改名 `executing_actor_ref`**。它与 Context 的 `actor_id`
  **重名易混**：在这个模型里它的含义是「该员工在执行链路上代表哪个已登记 actor」，
  改后既准确，也不再触发对 Context 字段名的保护。

### ③ 闭包对象缺 `required`

`config_authority` 声明了 `additionalProperties: false` 却没写 `required`。
已补 `may_change_config` 必填——**允许缺省会让「没填」与「不许改」在数据上无法区分**。

## 四、⚠️ 顺带发现的一个真问题：哈希锁有**两份**，且名字误导

加一个契约要改**三处**：p3 的 `P3_SHA256`、p4 的 `BASELINE_SHA256`、以及两边计数。

- `test_p3_contracts.py`：`BASELINE_SHA256`（26 条历史）+ `P3_SHA256`（9 条 p3）
- `test_p4_contracts.py`：`BASELINE_SHA256` —— **名字是基线，实际是四阶段并集**（35 条）

**这正是本项目反复吃亏的「两套真相」。** 分叉的后果很隐蔽：
一边放行另一边拒绝，或者**两边都放行而锁的值不同**（谁都没报错）。我为此连改了四轮才对齐。

**处置**：新增 `tests/infra/test_contract_hash_lock_consistency.py`（3 条）——
用 AST 取出两份字典（不执行测试模块），断言**同名文件的哈希一致**、
且**每一把锁都对得上磁盘**（防锁过期）。

## 六、已知限制

1. **只建模，不填数据**：登记表里仍无员工记录。数据一到位，
   `test_data_gap_register.py` 会报红，逼出「接数据 + 补员工页 + 让两项检查从 UNKNOWN 变可判」。
2. **没有配套的校验代码**：契约门校验**形状**，但"岗位限额是否覆盖全部风险等级"、
   "`executing_actor_ref` 是否真是已登记 actor"这两条**语义**约束目前只写在
   `x-employee-policy` 里，**尚无机器判据**（需要真实数据才谈得上校验）。
3. **`EmployeeRegistryExample` 只是极简占位**：完整示例对象**放不进去**——
   契约门禁止闭包对象出现 `tenant_id`，而完整示例需要它说明"一个租户一份文档"。
   所以完整示例写在 ADR 与本文里，不进 schema。
4. **`test_contract_inventory_gates.py` 的 28 条失败未修**（不在门禁内，属既有状态）。
5. `edge/` 独立部署树仍未建（ADR-0006 有意延后）；P5 仍待 8 项环境输入。
