# 管理后台 · 状态显示契约（`apps/web-admin/`）

- 日期：2026-10-05
- 依据：上游 §6「**控制台显示需带状态来源和更新时间，防止 UI 显示成功而 ERP 未过账**」；
  §17 A14「任务成功只由权威执行回执驱动，accepted/未知不显示已过账」；
  §10.1「管理权与业务批准权分开」；§15 `apps/web-admin/` 布局
- 判据：`scripts/gate.py --stages p2` **exit 0**；变异 `--phase p2` = **50/50 可捕获项全捕获**

## 1. 本轮交付的是**判定**，不是渲染

`apps/web-admin/src/status.js` 是一个**纯函数**：输入任务状态、命令状态、权威回执，
输出"界面上该显示什么结论 + 这个结论从哪来 + 什么时候更新的"。

把它抽成纯函数的理由很实际：

1. **判定可以被逐条钉住**——包括"看起来成功、其实没落账"那些反例；
2. **判定与 UI 框架无关**——换成任何渲染层都复用同一份口径；
3. **不依赖网络**——真实数据来自 API，但"怎么读这些数据"可复现。

配套还有 `src/view.js`（列表行、排序、筛选、空态、汇总卡片、HTML 转义）。

## 2. 一条压倒性原则：只有权威回执能说"已过账"

| 输入 | 它其实只表示 |
| --- | --- |
| `task.status = SUCCEEDED` | **编排跑完了** |
| `command.status = SUCCEEDED` | **执行侧认为成功了** |
| `receipt.authority_verified && posting_status = POSTED` | **账务真的过账了** |

所以实现是**默认一切未确认**，除非有权威回执明确说已过账。

> 反过来写（默认成功、有异常才降级）会让"**没拿到回执**"显示成成功——
> 那恰恰是上游要防的那件事。

门禁里的关键反例：

| 反例 | 期望 |
| --- | --- |
| task/command 都是 SUCCEEDED，但没有回执 | **不得**显示已过账，理由写明"未取得权威过账回执" |
| 回执自称 POSTED，但 `authority_verified !== true` | **不得**显示已过账（执行方自报不算账务事实） |
| 回执 `posting_status = NOT_CONFIRMED` | **不得**显示已过账 |
| 命令 `UNKNOWN`，即便任务已 SUCCEEDED | 显示**"结果未知，需对账"**——不能含糊成"处理中" |
| `posting_status = NOT_APPLICABLE` | 显示"**不涉及过账**"，与"未过账"分开 |

还有一条穷举：**"任务成功 × 命令成功"的所有组合，在没有回执时一律不得 POSTED。**

## 3. 结论必须带来源与更新时间

上游明文要求。所以每个结论都带 `sources`：task / command / receipt 各自的
`status`、`status_source`、`updated_at`。缺信息时**如实留空**，不伪造。

## 4. 列表页的坑：**不得自己数一遍**

最容易犯的错是按 `task.status === 'SUCCEEDED'` 统计"成功数"。
那个数字会与逐行结论**不一致**（逐行走的是回执判定），
于是同一屏上两个数字互相矛盾，而且**没人知道哪个对**。

所以 `view.js` 的汇总只调用同一个判定出口。门禁断言：

- 汇总与逐行**同源**；
- **"已过账"的计数不含仅编排成功的任务**（4 条全 SUCCEEDED、只有 1 条有回执 ⇒ POSTED=1、NOT_POSTED=3）。

另外两条工程约束：

- **排序把需要人看的排前面**（未知 > 需人工 > 失败 > 未过账 > 已过账）；
- **渲染必须转义**——后端字段直接内插会有注入风险，"只给内部人看"不是理由。

## 5. 技术栈的决定，以及为什么（需要你知情）

上游 §15 建议 Web 用 TypeScript。**我没有照做，理由是可行性与诚实性**：

- 本机 `npm view` **探测无返回**，registry 连通性未确认；
- 一个"装不上依赖的 React 工程"比"零依赖的可用模块"**更糟**——
  前者会被当成已完成，实际连构建都跑不起来。

所以当前交付：纯 JavaScript 模块 + JSDoc 标注类型，用 Node 内置 `node:test`
做门禁（**零外部依赖**，`node --test` 直接跑，44 条用例）。

`package.json` 里显式写了待补项与理由。**渲染层若改用 React/TypeScript，
替换的只是渲染；`status.js` 与 `view.js` 原样复用。**

## 6. 门禁接法

`tests/web_admin/test_status_contract.py` 把 Node 套件接进主门禁，并额外守住：

| 断言 | 为什么 |
| --- | --- |
| 应用与入口文件在位 | 不依赖 Node 也能守住"别被误删" |
| `package.json` 的 `dependencies`/`devDependencies` **为空** | 判定逻辑的验证不得绑定到 registry 可用性 |
| `status.js`/`view.js` 的 import 只指向相对路径或 `node:` | "零依赖"的机械判据 |
| 实际跑 `node --test` 且 `# pass` 非 0 | 防"0 个用例也算通过" |
| 套件源码里**关键反例在场** | 防"套件被删空但文件名还在" |

无 Node 时明确 `skip` 并写明原因——**不算通过**。

## 7. 顺带修好的一个**假证据**风险（重要）

给变异器加了 **变异后语法校验**。

原因：变异的目标是"注入语义缺陷"，而不是"让文件无法解析"。
若某条变异引入了语法错误，测试会因为**解析失败**而失败，
脚本却记成"门禁正确捕获"——**报告说门禁有牙，实际只是文件根本跑不起来**。

现在 `.py` 用 `ast.parse`、`.js`/`.mjs` 用 `node --check` 先验一遍，
语法不合法直接判 `[无效]`，不计入"已捕获"。

（第一版我写的 6 条 JS 变异里就有一条是括号不配对的——正好被这道校验拦住。）

## 8. 已知限制

1. **没有真实浏览器端到端验证**：判定与视图模型有 44 条单测，
   但"页面真的能跑起来"未验证（无框架构建）。
2. **未接真实 API**：`status.js` 的输入形状是按契约设计的，
   与真实 `GET /api/v1/tasks/{id}` 的字段映射**尚未联调**
   （字段名已在 `toRow` 里兼容 `status`/`updated_at` 两种写法）。
3. **只覆盖"任务列表 + 结论显示"**：员工/批准/发布/对账四个页面未做。
4. **`checkAuthoritySeparation` 只是判定函数**，尚未接到真实的角色配置上——
   上游 §10.1 的"管理权与批准权分开"目前只在代码层可校验，没有数据来源。
5. **未用 TypeScript**：理由见 §5；补齐需要 registry 可用。
