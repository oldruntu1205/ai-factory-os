## 一、补的是什么口子

上一轮的未接线守卫只扫 `services/` 与 `packages/`，
而我上一轮**明确写了**这个限制：**`apps/`（JS）未纳入**——而 10-05 的事故
（`approval.js` 留下 `if (false)` 把判据禁用）**正发生在 `apps/`**。

本轮补上，并顺带发现一个**安全判据的缺口**。

## 二、审计结果：12 个导出在生产侧没有消费者

`apps/` 21 个导出，12 个生产无消费者。逐个核实后分两类：

### 正当例外（列表视图面 + 契约枚举）

| 导出 | 为什么正当 |
| --- | --- |
| `buildListView` / `summarizeLabels` / `renderRows` / `summarizeApprovals` | 列表视图模型：当前页面只有**单条查询**，没有列表页 |
| `TASK_STATES` / `COMMAND_STATES` / `POSTING_STATUSES` / `DISPLAY_OUTCOMES` / `DECIDABILITY` / `CHECK_RESULTS` / `decidabilityLabels` | 契约枚举，供界面文案与校验引用 |

### ⚠️ 安全判据：`checkAuthoritySeparation` 没有数据源可接

它实现的是**上游 §10.1「配置权与批准权分离」**——一条**必须**项。
而它在生产里 **0 消费**。

**我核查了能否接线，结论是：不能，因为缺数据源。**

| 需要的数据 | 实测 |
| --- | --- |
| 「谁能改配置」名单 | `services/_kernel/registry.mock.json` **只有 `actors` 与 `delegated_scopes`，没有配置权限映射** |
| 生产登记表 | 登记表自己的 note 写着「生产登记表由 control-plane 的 Release Registry 提供，**待冻结**」 |

**我不凭空造这份名单**——编一份假的配置权清单会让这条判据变成**安慰剂**：
它会在测试里"绿着"，而实际上从未对任何真实身份做过判定。

### 已确认的缓解（不是"待办"，是真的拦住了）

后端 `transactions.revalidate_before_execution` 的 `duties_separated`：

```python
approver = (approval or {}).get("approver_ref")
requester = command.get("actor_id")
flags["duties_separated"] = bool(approver) and approver != requester
if not flags["duties_separated"] and approval is not None:
    reasons.append("DUTIES_NOT_SEPARATED")   # ⇒ 阻止执行
```

**最危险的"自己批自己"已被拦住。** 缺的是外层那圈：
「同一人**既能改配置、又能批准**」——那需要配置权名单。

**接线条件已写进登记理由**：control-plane 暴露配置权名单后，
在 `server.mjs` 的批准决定路径调用它，未分离即拒绝
（与 `APPROVER_NOT_CONFIGURED` 同一处置风格）。

## 三、守卫的构造（与 Python 侧同构，但多踩了一个坑）

`tests/infra/test_apps_export_surface.py`，9 条。

### 「生产代码」必须包含**两类**消费者

第二类最容易漏：**`public/index.html` 里内联的浏览器脚本**。
漏掉它会把在用的导出误判为死代码。

### 两条自检：一条不够

| 自检 | 证明什么 |
| --- | --- |
| 注入样本必须报出无消费者的导出 | **能不报**（识别能力） |
| `_exported_names` 必须解析**每一种**导出语法 | **能全部解析**（不漏读） |

**第二条是被一次变异逃逸逼出来的。**

## 四、⚠️ 又一次变异逃逸，暴露了自检的短板

我加的第一版自检只验"**能不报**"。于是这条变异逃逸了：

```
[逃逸] apps/ 导出探测器漏掉一种导出语法（守卫自己变瞎）
```

把正则从 `export\s+(?:const|let|var)\s+(\w+)` 收窄成 `export\s+const\s+(\w+)`
（漏掉 `let`/`var`），门禁**仍然全绿**——因为**本仓恰好没有 `export let/var`**，
收窄的后果在真实数据上**不可观测**。

**这是"守卫自我验证"的普遍短板**：只证明"能在已知数据上工作"，
没证明"能处理全部输入形态"。将来有人写 `export let`，就会被**静默漏掉**——
漏掉的导出不进判据，等于**无声放弃**对它的守护。

**修法**：直接喂样本，把各种导出语法逐条钉住，**不依赖本仓恰好有没有用到**。

> 教训与上几轮同源：**守卫必须证明自己能识别，而不只是"没报错"。**

## 五、UI 冒烟：页面渲染此前完全没有自动覆盖

同一类事故在 UI 上已发生**两次**（成交明细撑长页面、批准判定被禁用），
而**页面的渲染没有任何自动覆盖**：判定的单测测的是 `src/*.js`，
页面用的是**服务端算好的结论** + 自己的渲染。

本轮加两条**结构事实**断言（不做截图比对——脆弱且需要浏览器）：

1. 关键元素 id 在（`approvalId` / `queryApproval` / `approvalResult`）；
2. 页面渲染的是**服务端结论**（`d.outcome` / `d.label`），
   且不得自行宣称"已过账"；
3. **内联脚本语法必须合法**（改坏了 = 控制台白屏）。

**核查过的一件事**：页面**没有**重写判定逻辑——`d.outcome` 来自服务端
（`deriveDisplayStatus`），页面只渲染。这是对的，不是"两套真相"。

所以"破坏内联脚本语法"这条变异**不是靠语法检查报红的**——
真正报红的是我新加的 `node --check` 内联脚本断言。这个区分很重要：
**否则会把"脚本根本跑不起来"误记成"守卫抓住了语义缺陷"。**

## 七、已知限制

1. **探测器的判据是启发式**：要求"生产无消费者 **且** 测试有引用"。
   若新增导出连测试都没引用，探测器抓不到（实测踩过）。
   真实开发中"加了导出顺便写测试"是常态，所以这个边界可接受；
   但**它确实是个盲区**，不假装覆盖。
2. **`escapeHtml` 在页面里有一份自己的实现**（`view.js` 也有一份）。
   两份转义实现理论上会分叉。当前未统一，**未纳入本轮**。
3. **`checkAuthoritySeparation` 仍未接线**（缺数据源），已写明接线条件。
4. **UI 冒烟只守结构事实**，不验像素/交互；真实交互仍靠人工或浏览器自动化。
