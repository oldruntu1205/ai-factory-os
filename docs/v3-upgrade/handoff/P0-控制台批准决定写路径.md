## 一、做了什么

管理后台此前**只有只读面板**——看得到状态，做不了决定。
本轮加上**批准决定**写入路径，并让它在 **http://127.0.0.1:8300** 真实可用。

"能写"意味着后台拿到了**权限**，所以本轮的实质工作不是"加个按钮"，
而是**把三条越权通道逐个堵上**。

| 约束 | 拒绝时响应 |
| --- | --- |
| ① 未配置决定人 ⇒ 拒绝写 | `403 APPROVER_NOT_CONFIGURED` + **后端零写请求** |
| ② 说明里写「同意/批准」⇒ 拒绝 | `400 NATURAL_LANGUAGE_APPROVAL_REJECTED` |
| ③ 决定必须**记名**，由后端复核 | 提交时 `context.actor_id` = 配置的决定人；响应回报 `actorId` |

界面**明示**"将以 `<actor>` 的身份记录这次决定……这不是'你'的身份"——
否则界面看似"我批的"，实际是某个账号批的。

## 二、绑定：一处我**无法**替调用方读出来的事实

最初设计是"绑定由后台从批准的既有事实读出，不接受前端传入"。**实测做不到**：

| 尝试 | 结果 |
| --- | --- |
| `GET /api/v1/approvals/{id}/fact` | 对**未决定**的批准返回 **`409 APPROVAL_NOT_DECIDED`**，**响应不含绑定** |
| "读取待决批准绑定"的 GET 接口 | **全仓没有** |
| 直接读 `approvals` 表 | 只有**已决定**的批准 |

所以绑定只能由**知情操作方**提供。**这不是漏洞**——后端会拿它与该批准
**已记录的 `binding_hash`** 比对。实测：

| 提交 | 结果 |
| --- | --- |
| 真实绑定 + 通过 | **200**，决定人 `user-approver` 记入事实 |
| **篡改一个绑定字段** | **409 `APPROVAL_BINDING_CHANGED`** |

> 前端改字段没用——真正的校验在后端。后台只做**结构性预检**（字段齐不齐），
> **不假装**能读回绑定；未提供就**明确拒绝**，而不是猜一份。

## 三、⚠️ 事故：我强杀变异脚本，**把变异留在源码里**

### 发生了什么

变异测试跑得异常久（30 分钟）。我用 `Stop-Process -Force` 强杀了它。

**问题**：变异脚本的还原靠 `try/finally`，而**硬杀不会执行 `finally`**。
于是 `apps/web-admin/src/approval.js` 里留下了：

```javascript
const natural = looksLikeNaturalLanguageApproval(comment);
if (false) {          // ← 变异残留：把「说明文字不能当授权」整条禁用
```

**这条判据被完全关掉了**，并且在此后还成功提交了一次决定
（本地判据已被禁用，请求直接打到后端）。

### 为什么它当时没被发现

1. **`apps/` 在本仓未被 git 跟踪** —— `git status` / `git diff` 都看不见它。
   我一直靠 git 判断"改了什么"，而这里**根本没在版本控制里**。
2. **原有 JS 用例测的是判据函数本身**，不是"调用方到底有没有用它"。
   `approval.test.mjs` 断言 `looksLikeNaturalLanguageApproval("同意").naturalLanguage === true`
   ——这**依然通过**，因为它测的函数没被改，是**调用点**被改了。

### 它最终是怎么被发现的

不是被门禁抓住的。是我**新写的 Python 用例**断言"说明里出现「同意」必须 400"，
**失败了**，才顺着查出来。也就是说：**发现它纯属运气**（恰好这一轮在写覆盖它的用例）。

### 修法（两层）

1. **还原源码**：`if (false)` → `if (natural.naturalLanguage)`（函数契约返回的正是这个字段）。
2. **堵住这条路**：给 `scripts/mutate.py` 加**起始完整性预检** `preflight_tree_is_clean()`——
   判据是**双条件**（变异文本在场 **且** 原文不在场，避免注释误报），
   任一阶段发现残留就**拒跑并列出是哪个文件**。

**自证有效**（否则是空转守卫）：

```
注入前预检: 干净
注入后预检: ["apps/web-admin/server.mjs: 仍含变异文本 'if (false) {'"]
还原后预检: 干净
```

### 我的流程错误（不只技术问题）

我在**明知会破坏状态**的情况下强杀了正在改源码的脚本。
正确做法是：等它跑完，或先确认"此刻是否有文件处于变异态"。
**这是一次可以避免的事故，责任在我。**

## 四、测试

新增 `tests/web_admin/test_decision_write_path.py`（14 条，含 4 条参数化）。

### ⚠️ 为什么是 Python 而不是 `node --test`

我最初写成 `apps/web-admin/test/decision.test.mjs`，结果**整个套件挂死**（永不返回）。
根因是**嵌套 `node --test`**：门禁 → `node --test`（父）→ 管道 spawn 测试文件（子）
→ 我又 spawn 管理后台并用**管道**读回端口。父与子互相等管道 flush ⇒ 死锁
（与本机沙箱对管道捕获的限制同源）。

修法不是绕过沙箱，而是**去掉这层嵌套**：门禁本来就跑 Python 包装层，
所以直接用 Python 起进程、**stdout 走临时文件**（不用管道读端口），行为一样、无死锁面。

### 踩到的另一个测试陷阱

我最初断言"被拒绝时 `backend.received.length === 0`"，**测试失败**——
因为后台起服务后会对后端做**健康探测**（`GET /health/live` × 3），那不是"写"。
改成只筛 `/decisions` 之后才正确。

> **"后端收到 0 个请求"这种断言，必须先确认没有别的正当请求混进来。**

## 五、顺带修掉的一个真实小 bug

`server.listen` 回调原来打印**配置的** `ADMIN_PORT`。
`V3_ADMIN_PORT=0`（交给系统分配，测试要用）时会打印 `0`——一个不可连接的端口。
改为打印 `server.address().port`。
