## 2. 关键语义实现要点（逐条对应上游）

| 上游条款 | 实现 |
| --- | --- |
| §5 批准绑定对象/payload哈希/策略版本/动作范围/有效期 | `approval_binding_fingerprint` 六维指纹 + 逐维核对，**任一维变化即阻止执行** |
| §12 `AUTHORIZED` 不是永续许可 | `revalidate_before_execution` 在 EXECUTING 前重验批准有效期、对象版本、权限、策略版本 |
| §5 禁止 UNKNOWN 换键重发/直接补偿 | `UNKNOWN_ALLOWED_ACTIONS` 白名单 + `UNKNOWN_FORBIDDEN_ACTIONS` 黑名单，两组**互斥**且可被契约断言 |
| §5 先恢复实物再账务冲销 | `compensation_order` 强制实物域全部排在账务域之前；域内逆序 |
| §5 已发货/已过账必须分支 | `plan_compensation` 把它们放进 `branches`（`RETURN_OR_CREDIT_NOTE` / `LEDGER_REVERSAL`，需审批），**不走普通冲销** |
| §5 补偿失败进人工队列 | `compensation_outcome` 失败即 `MANUAL_REVIEW`，**绝不谎报 COMPENSATED** |
| §12 取消只停未开始步骤 | `plan_cancellation` 区分可停止/需确认/需补偿，并给出"能否置 CANCELLED"的判据 |
| §12 租约与 fencing | `acquire_lease` token 单调递增；`Lease.valid` 拒绝旧 worker 与过期租约 |
| §5 哈希由可信服务计算 | `canonical_payload_hash` 固定输入形状、无时间/随机量 ⇒ 同一绑定永远同一哈希 |
| §10.4 Transaction 复核哈希 | 收执路径要求能用同一规范输入重算一致，否则 409 |
| §5 能力位不足禁止无人值守高风险写入 | `write_admission` 三项能力位全 true 才放行；无论是否放行都强制台账/对象锁/人工对账 |
| §13 每 owner 独立 schema/role + RLS + 无跨 owner 授权 | `storage.generate_owner_ddl` + 5 个不变量函数，全部进 CI |

## 3. 本批实际修掉的缺陷（都是实测发现）

| 缺陷 | 发现方式 | 修法 |
| --- | --- | --- |
| **跨 owner 授权检测漏检最典型的越权形态**（`GRANT USAGE ON SCHEMA <别人的> TO <自己的角色>`） | 变异测试 | 改为正则拆解「被授权对象 / 被授权者」再比对 owner；补防回归用例 |
| `data_class_rules` 形状错（用了 `max_class`，契约要求 `unknown_class` + `inherit_highest_class`） | P3 运行验收的契约校验 | 按 `tool-spec.json` 修正 mock 与投影 |
| 工具目录只有 11 字段，契约要求 15 个 | P3 运行验收的契约校验 | 补齐 `timeout`/`retry_policy`/`input_schema`/`output_schema`/`data_class_rules` |
| GET 接口用 `_p1_context` 导致恒报 `NESTED_TENANT_MISMATCH`（GET 无 body） | P3 运行验收 | 新增 `_p3_get_context`：Context 只从 `X-Api-Context` 头取 |
| 全局表豁免判定顺序错误（先 assert 后豁免） | P2 存储门禁 | 豁免判定前置 |
| 豁免表键格式错（用 `schema.table` 而 schema 名 ≠ owner 名） | P2 存储门禁 | 统一改为 `owner.table` |
| 权限判定用朴素子串（`NOSUPERUSER`/`BYPASSRLS OFF` 会被误判为过度权限） | 主动防回归 | 改为识别 ON/OFF 形态 + 防回归用例 |

**L1 缺陷（已按纪律上报并修复，L2 未自行改测试）**：
① P3 夹具把 `schema_ref` 填成标识符 `task-demo`，违反自身 pattern（33 用例红）；
② P1.5 清单门禁再次耦合全局文件集合（第 3 次同类）→ 已改为登记处驱动，
并新增 28 个回归用例覆盖 P4/P5 隔离。

## 6. 已知限制

1. `unattended_high_risk_write_allowed` 对**低风险但缺能力位**的工具同样为 false
   （契约要求）；高低风险由 `high_risk` 判定区分。
2. 规范哈希的输入形状由 `canonical_binding_material` 固定；**真实入参 schema 的
   规范形式待冻结**（外部接口字段映射未提供）。
3. `reconcile` 把"置 UNKNOWN"与"查询源系统"合成一次调用，因此
   `query_attempt_count` 恒 ≥ 1，契约中 `query_attempt_count == 0 → candidate_actions
   == ["QUERY_SOURCE"]` 那个分支**当前不可达**（代码注释已标注）。
4. 收敛记录的 `query_evidence_hash`、步骤账的 `pre_state_hash`、补偿回执均为**占位值**，
   未接入真实适配器台账与真实前置状态快照。
5. Saga 步骤账由请求携带（`steps` 字段），**真实补偿计划文档格式待冻结**；
   当前只保证契约形状与顺序/分支/失败语义正确。
6. **并发只在单进程多线程下验证**（`http.server` 的请求处理方式限制）：
   跨进程真正并发下的 CAS 行为需要 DB 层约束才能严格保证（属 P2/P3 的 persistence 落地）。
7. `tool-executions/controlled` 已接线，但 adapter 仍是 **Mock 边界**：
   派发只写审计意图与派发引用，不产生真实外部副作用。
8. §13 的 DDL **未在真实 PG 上执行过**；不变量是门禁断言，不是执行证明。
9. `backend/`（V2.1 在产单体）仍一行未改。
