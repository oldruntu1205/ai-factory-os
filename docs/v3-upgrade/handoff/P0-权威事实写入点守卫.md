# 权威事实写入点守卫（把"凭空写成功"从静默可能变成必须登记）

- 日期：2026-10-05
- 依据：上游 §6「防止 UI 显示成功而 ERP 未过账」；§17 A14
- 判据：`scripts/gate.py --stages p0,p1,p15,p2,p3,p4,assertions` **exit 0**（1295 用例）；
  变异 **133 个可捕获项全捕获**（p2 74、p3 29、p4 17、p15 7、p1 6）

---

## 一、为什么做这件事：同一类缺陷在一个会话里出现了三次

| 次数 | 缺陷 | 表现 |
| --- | --- | --- |
| 1 | 补偿路径伪造回执（上一轮修） | "什么都没做"的补偿报 `COMPENSATED` |
| 2 | `posting_status` 硬编码（更早一轮） | 界面会把未过账显示成已过账 |
| 3 | 补偿回执 `command_id` 与命令不一致 | 照回执查命令查不到 |

三次的共同形状是：**某处代码凭空写下一个"成功"断言**，
而没有任何真实执行支撑它。

**这类缺陷门禁抓不到**——它不违反任何单点断言，只是让断言"看起来成立"。
所以每次都要靠**事后审计**才发现，而审计依赖"我恰好看到了"。

**本轮把它变成机械守卫。**

## 二、审计：全仓只有 3 处字面量权威断言，且全部合法

新增 `tests/infra/test_authority_fact_writers.py`，用 AST 扫描
`services/_kernel/routes.py`，找出**字面量**写
`authority_verified: True` / `business_success: True` 的函数：

| 函数 | 白名单理由 |
| --- | --- |
| `_handler_p15_receipt` | 外部权威回执经接口送达，由可信执行方给出 |
| `_handler_p3_reconcile` | 向源系统查询后记录结论，结论来自源系统而非自报 |
| `_p3_receipt` | **已知例外**：合成夹具，构造测试场景的步骤账（描述"一个已完成步骤的形状"），不是在声称某个动作刚刚做过了 |

**扫描结果：恰好这 3 个。补偿路径已不在其中** ——
这正是上一轮修复的直接证据。

### 顺带审计到的两处，结论是**不是缺陷**

1. **`_handler_tool_execution`（L750）硬编码 `"status": "SUCCEEDED"`**
   —— 它**就是适配器（Mock 权威源）**，且设计良好：
   - 只接受受限服务身份 `x-v3-caller: transaction-service` + `execution_permit_ref`；
   - `_ensure_receipt()` 的注释明确写着「这里**不直接改命令状态**，
     因为"命令成功"只能由 Transaction 依据权威回执判定」；
   - 回执真的写进 journal（幂等）。
   一个 Mock 适配器返回 SUCCEEDED，就是它该做的事。

2. **`transactions.compensation_outcome`（L400）返回 `saga_status: COMPENSATED`**
   —— 它是**纯函数**：由调用方传入 `executed` / `failed`，只有 `failed` 为空才返回
   `COMPENSATED`。它**不自己声称**任何东西。

## 三、守卫的判据与边界

**判据**：权威事实只有两种合法来源（外部回执送达、查源系统得出结论）。
凡是**字面量**写权威成功断言的函数，**必须在白名单里**；
新出现的函数会被点名，必须解释"它凭什么是权威来源"。

**三条配套断言**：

| 断言 | 为什么 |
| --- | --- |
| 白名单外出现字面量断言 ⇒ 报红 | 核心判据 |
| 白名单里不得留**已不存在**的函数 | 否则白名单退化成没人维护的历史清单 |
| 每个白名单项必须**写明理由** | 无理由的白名单等于没有约束 |

**能力自检**（用构造样本证明守卫有牙）：

```python
# 应**正好**报出字面量写成功的那个函数，且不误报派生写法
assert names == {"_handler_something"}
```

样本里**混了一个合法项**（`bool(record.get('receipt'))` 的派生写法）——
否则"全报"也能通过，那同样是能力不足。

### 边界（诚实说明）

- **只查字面量**。`bool(receipt and receipt.get(...))` 这种**派生**写法不受约束
  —— 那正是我们想要的形态，所以不拦。
- **不能**证明白名单里的函数真的做了核查。它只保证**新增写入点必须被看见**。
- **不查** `SUCCEEDED` 状态字符串（它出现在许多合法的视图构造里，
  逐个判定噪声太大）；只查回执侧的"权威/业务成功"断言。

> 净效果：把"凭空写成功"从**静默可能**变成**必须显式登记**。

## 四、顺带发现：一处"有单测但从未接线"的逻辑

审计时发现 `transactions.plan_compensation` / `compensation_outcome` /
`plan_cancellation` 是**纯逻辑、有单测，但从未被任何 HTTP 路由调用**——
Saga 的实际顺序判定写在 `_handler_p3_saga_compensate` 里，是**另一处实现**。

**当前两处口径一致**（物理域先于账务域），所以**不是缺陷**。
风险在于：两处会各自演进、悄悄漂移，而只有一处真正生效——
于是"单测说顺序对"与"实际顺序对"可能不再等价。

处理方式：**不重构**（那会动已验证的路径），而是加两条断言把两处**钉在一起**：

- 契约层 `plan_compensation()["recovery_order"]` 必须是 `[PHYSICAL, ACCOUNTING]`；
- 生效层必须有 `PHYSICAL_RESTORE_REQUIRED` 判据、且 `recovery_order` 是**两项对象**
  （契约用 `prefixItems` 固定，不是字符串数组）。

> 谁先改，谁就会在这里报红。

## 五、已知限制

1. **守卫只覆盖 `routes.py`**。已手工核查其余内核模块
   （`transactions.py` / `events.py` / `edge.py` / `projection_store.py` /
   `governance.py` / `vault.py` / `storage.py` / `migration_runner.py`），
   未发现字面量权威断言；但**未做成机械守卫**（它们目前确实没有这类写入点，
   加进来会是空转）。
2. **守卫不替代评审**：它只能保证"新增写入点被看见"，
   不能判断白名单里的函数是否真的核查了。
3. **`plan_*` 三组纯逻辑仍未接线**：只加了防漂移断言，没有统一成单一来源。
   统一需要重构验证过的路径，收益不抵风险。
