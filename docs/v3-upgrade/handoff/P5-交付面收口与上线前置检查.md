# 交付面收口：覆盖报告改为生成物 + 上线前置检查器

- 日期：2026-10-05
- 依据：上游 §14（部署与运维）、§17（必须验证的验收断言）
- 判据：`scripts/gate.py --stages p0,p1,p15,p2,p3,p4,assertions` **exit 0**（1332 用例）；
  变异 **145 个可捕获项全捕获**

---

## 一、为什么做这个（连做 5 轮守卫之后，回到交付面）

前 5 轮反复在修"判据存在却没被使用"这一类问题。本轮换上**交付视角**问一句：

> **如果明天有人接手，他能不能从证据里看出"现在到哪了、还差什么"？**

答案是不能。实测发现两个具体问题。

## 二、问题①：覆盖报告是**手写的，因此必然过期**

`docs/v3-upgrade/evidence/A01-A14-断言覆盖报告.md` 实测写着：

| 报告里写的 | 实际情况 |
| --- | --- |
| 「引用的测试节点 **75**」 | 库存已涨到 **95** |
| A14 缺口「**UI 面未接入（无前端）**」 | 早已不成立——`apps/web-admin` 显示契约有 44 条用例 |

而且**没有任何门禁核对它**。

> **手写证据会漂移，而漂移的证据比没有证据更危险：它看起来权威。**

### 修法：改成生成物 + 门禁核对新鲜度

新增 `scripts/render_assertion_report.py`：

- **唯一输入**是 `tests/assertions/assertion_inventory.py`（门禁逐条核对的机器可读清单）；
- 生成过程**无网络、无随机、无墙钟** ⇒ 同一份库存必然产出同一份报告；
- 新增门禁 `test_coverage_report_is_generated_and_not_stale`：
  报告与清单不一致即报红，并**指出首个差异行**（不是只说"不一致"）。

### 自证（两条，都是机械的）

| 自证 | 结果 |
| --- | --- |
| 生成幂等 | 两次生成 **SHA256 一致** |
| 新鲜度有牙 | 改清单但不重新生成 ⇒ **门禁报红**（实测 `改清单但不重新生成报告 ⇒ 门禁报红: True`、`已还原清单: True`） |

另加一条：报告**不得出现当天日期**——否则 `--check` 永远报红，门禁会被人为绕过。

## 三、问题②："阻塞在目标环境信息"是个**不可执行的结论**

P5（受限生产）一直这么记着。但它既不能验证、也无法知道进展——
**没有名字的阻塞等于没有阻塞**。

### 修法：`scripts/preflight_deploy.py`

把阻塞拆成**两类互不混淆的输出**：

| 类别 | 能否在仓库判定 | 输出 |
| --- | --- | --- |
| **仓库内就绪度** | ✅ 能 | `[就绪]` / `[缺失]`（缺失 ⇒ 退出码 1，因为这是我能修的部分） |
| **目标环境事实** | ❌ 不能 | `[阻塞]` 逐条列名 + 说明为什么仓库里判定不了（**不是失败，是待办输入**） |

**实测输出**（本机运行）：

```
[就绪] 仓库内部署就绪件 11 项
[缺失] 无 —— 仓库侧就绪件齐备
[清单] infra/deployment/manifest.yml
    frozen = false（生产登记表未冻结时**必须**如实写 false）
[阻塞] 目标环境必须提供的输入 8 项
  1. 目标机器与网络位置      为什么需要：决定部署形态、网络域落地与防火墙策略
  2. 生产数据库与账号        为什么需要：决定迁移执行方式与备份策略
  3. 域名与证书              为什么需要：决定反向代理与暴露面
  4. 停机窗口与回滚时限      为什么需要：决定上线方式（滚动/蓝绿）与回滚判据
  5. 凭据投放方式            为什么需要：密钥只能从密钥管理/受限挂载注入，绝不进仓
  6. 生产登记表              Mock 登记表待冻结（见 manifest.frozen）
  7. 监控与告警接收端        为什么需要：决定 /health/* 与 metrics 的消费方
  8. 现场验收人              P3/P4 现场验收签署；无签署不得进入受限生产

结论：**仓库侧就绪**；部署阻塞已收敛为 8 项目标环境输入。
```

**部署阻塞从一句话变成了一份 8 项的待办输入清单。**

### 检查器当场抓到自己的 bug

第一次运行报 `✗ frozen 取值不是布尔字面量`——因为清单里写的是：

```yaml
frozen: false          # 生产冻结状态：**未冻结**（外部依赖未到位，见 blocked_by）
```

我这个**零依赖**的检查器把行尾注释也当成了取值。
修法是加 `_strip_yaml_comment()`，并**为它单独写了一条用例**。

> 这是"工具自己也是被测对象"的一个实例：**检查器报的问题，先怀疑检查器。**

## 四、新增门禁

`tests/infra/test_delivery_tooling.py`（6 条）：

| 用例 | 防什么 |
| --- | --- |
| 生成幂等 | 报告混入时间戳/随机 ⇒ `--check` 永远红 |
| 无墙钟依赖 | 同上（本项目既有约定：**判定函数不得读墙钟**） |
| 就绪件齐备 + 阻塞列名 | "阻塞"变成有名字的清单 |
| 清单如实未冻结 | 把待冻结的外部依赖说成已完成 |
| YAML 行尾注释被剥掉 | 检查器自己误报 |
| `--json` 可解析且带结论 | 供部署前门禁消费 |

新增变异 3 条：改清单不重新生成报告、检查器不剥注释、生成器混入当天日期。

## 五、已知限制

1. **阻塞现在有名字了，但仍是阻塞**。P5 不会因为这份清单而变成"可做"——
   它仍需要目标机器、生产库、停机窗口、现场验收人。
   本轮做的是**把不可执行的"阻塞"变成可核对的清单**，不是消除阻塞。
2. **就绪件清单是人工维护的**（`REQUIRED_ARTIFACTS`），不是从别处推导的。
   新增部署件时需要同时登记；遗漏只能靠评审发现。
3. **检查器不连目标环境**（零依赖、零网络）。它的 `--json` 是给
   "部署前在目标机上跑一次"用的，但那一步**尚未在真实目标机验证过**。
4. **覆盖报告只覆盖 A01–A14**：P2/P3/P4 的交付细节仍散在 `handoff/` 各文档里，
   没有统一的机器可读索引。
