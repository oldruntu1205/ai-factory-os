  **防止 UI 显示成功而 ERP 未过账**」；§17 A14

## 一、这一轮为什么必须做"能打开"

前两轮我交付的是**纯 JS 判定模块**（44 + 23 条单测），但**没有页面**——
按你的要求（「UI 改动做完必须立刻让它在正在用的入口上真实可见」），
「有模块、能测」**不等于**「能打开、看得见」。

所以本轮把它做成**真能打开的控制台**：

```
python tools/v3_dev_cluster.py start     # 起 8 个服务单元（标准端口 8101-8108）
python tools/v3_dev_cluster.py demo      # 造一条走完整链路、带权威回执的命令
node apps/web-admin/server.mjs           # 打开 http://127.0.0.1:8300
```

## 二、为什么是"零依赖 Node 服务"而不是 React 工程

本机 npm registry 连通性未确认（`npm view` 探测无返回）。

**一个"装不上依赖的 React 工程"比"零依赖的可运行服务"更糟**：
前者会被当成已完成，实际连构建都跑不起来。所以：

- `server.mjs` 只用 Node 内置模块，托管页面 + **同源代理**后端；
- 判定逻辑仍走 `src/status.js` / `src/approval.js`——**已被 67 条用例钉住的那套纯函数**，
  页面只负责画，不重复实现一份口径（两份必然分叉）。

**同源代理还顺手解决两件事**：浏览器不必跨域（后端在 8102/8107），
且**服务身份凭证留在服务端**，页面里既没有 token 也没有内部地址。

## 三、三个面板，每个都在回答一个具体问题

| 面板 | 回答什么 | 数据来源 |
| --- | --- | --- |
| 任务结论 | 编排跑到哪一步 | `GET /api/v1/tasks/{id}` |
| **命令与权威回执** | **账务过账了吗** | `GET /internal/v1/commands/{id}/execution-record` |
| 批准可决定性 | 这条批准现在能不能决定 | `GET /api/v1/approvals/{id}/fact` |

**没有"任务列表"面板**——因为系统**没有列表接口**（只有按 id 取单条）。
这一点在页面上如实写明，不用假数据凑一个列表出来。

## 四、联调中抓到的真实缺陷（这类问题只有真跑才会暴露）

### 缺陷 1：`GET /internal/v1/commands/{id}` 对 P3 命令**直接 500**

真实跑通一条 P3 交易链路后去读命令，服务端 `KeyError: 'source_system'`，
连接被掐断（`RemoteDisconnected`）。

根因：**命令记录有两种形状**，由两条路径创建：

| 来源 | 有 | 没有 |
| --- | --- | --- |
| P0/P1.15 命令 | `source_system`、`receipt_refs` | `binding`、`authority_receipt`、`lease` |
| P3 受控交易 | `binding`、`authority_receipt`、`lease` | `source_system`、`receipt_refs` |

视图按前者的键硬取，碰到后者就崩。**修法是全部用 `.get()`。**

**它此前测不出来的原因**：路由可达性测试用的是占位 command_id，
走到 404 就返回了，从没让"一条真实存在的 P3 命令"走过这个视图。
所以本轮补了回归断言（`test_command_get_view_supports_transaction_created_records`）。

### 缺陷 2：我自己把契约测红了（诚实记录）

修缺陷 1 时，我顺手把 `posting_status` 等 P3 字段塞进了同一个响应。

结果 `test_responses_conform_to_contract_schemas` **当场报红**：
`command-status.json` 是 **`additionalProperties: false`**，只允许 16 个字段。

**这是契约在正确地拦住我。** 两个视图的形状由**各自的契约**规定：

| 接口 | 契约 | 有 `posting_status`？ |
| --- | --- | --- |
| `/internal/v1/commands/{id}` | `command-status.json` | **否** |
| `/internal/v1/commands/{id}/execution-record` | `p3-command.json#/$defs/View` | **是** |

正确修法是**读对接口**，而不是改宽契约。我第一版还把 `posting_status` 断言
加在了前者上，等于用错误的期望去测正确的实现——也一并改掉了。

### 缺陷 3：任务不存在却显示"处理中"

`deriveDisplayStatus` 对"没有任何状态输入"的默认答案是「未过账 / 处理中」。
对"查不到这条任务"来说这是**错的**，而且错得危险——
看的人会以为"任务在跑"，实际是**这条任务不存在**。

已修：有明确失败原因时结论改为「无法判定 + 说清原因」。
宁可显示"查不到"，也不要给一个偶发正确的猜测。

### 缺陷 4：身份头缺一半

我先只发了 `X-V3-Identity`，于是每次都 401「缺少或无效的服务身份凭证」。

真相是两个头职责不同：

- `Authorization: Bearer …` 才是**身份凭证**（`_has_identity` 只认它）；
- `X-V3-Identity` 是"这个身份代表谁"的**租户归属**（`_identity_tenant`）。

## 五、一个必须知道的事实：**"已过账"今天不可达——这是对的**

实测造出的一条命令：`status=SUCCEEDED`、`authority_verified=true`、
`business_success=true`，但 **`posting_status` 仍是 `NOT_CONFIRMED`**，
界面显示「**权威回执确认未过账**」。

核查全仓：`posting_status` 在 **5 处回执构造里全部写死为 `NOT_CONFIRMED`**，
`posting_evidence_ref` 恒为 `None`。也就是说**今天任何输入都产生不出"已过账"**。

**这不是缺陷**：真实过账凭证（ERP 的过账确认）是上游明列的外部依赖，尚未接入。
界面对一条刚跑完的命令显示「未过账」是**正确且刻意**的——
它正是上游 §6「防止 UI 显示成功而 ERP 未过账」要的效果。

这与 `approval.js` 里那条「当前数据条件下没有任何输入能得出 DECIDABLE」
是同一类处理：**缺数据时说缺，不假装已有。**

## 六、已知限制

1. **没有"任务列表"**：系统无列表接口，页面如实说明而不是造假数据。
2. **任务→命令的关联走不通**：任务视图有 `command_refs` 字段，
   但**全仓没有任何代码路径写入它**（编排推进属后续阶段）。
   所以控制台的三个面板是**并列查询**，不是"点进去下钻"。
   我没有伪造这条关联——那正是上游要防的"UI 显示与事实不符"。
3. **认证是 mock**：`Bearer p0-test` + 固定 demo 上下文；
   真实 SSO 与 tenant/factory 边界是外部依赖。
4. **页面无端到端浏览器验证**：我验证的是"HTTP 200 + 真实 API 数据 + 判定正确"，
   **没有**用无头浏览器截图或跑 DOM 断言。
5. **未用 TypeScript**：理由见 §2；补齐需要 registry 可用。
6. `tools/v3_dev_cluster.py` 是**开发工具，不参与门禁**——
   它在标准端口起服务，而门禁用随机端口，两者互不干扰。
