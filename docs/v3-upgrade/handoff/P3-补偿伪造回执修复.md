# 修掉一处伪造的权威回执（Saga 补偿链）

- 日期：2026-10-05
- 依据：上游 §5（Saga 补偿）、§6（**防止 UI 显示成功而 ERP 未过账**）、
  §17 A08 / A14
- 判据：`scripts/gate.py --stages p0,p1,p15,p2,p3,p4,assertions` **exit 0**（1279 用例）；
  变异 **132 个可捕获项全捕获**

---

## 一、缺陷：补偿路径**伪造**了一份权威回执

`_handler_p3_saga_compensate` 的"常规补偿"分支里，旧代码直接写上：

```python
"command_status": "SUCCEEDED",
"authority_receipt": {
    "authority_verified": True,
    "business_success": True,
    "command_id": f"command-comp-{uuid.uuid4().hex[:12]}",   # ← 另起一个 uuid4
    ...
},
```

而那条补偿命令**从未派发、从未执行、也没有任何回执**。

它同时违反三件事：

| 违反 | 说明 |
| --- | --- |
| **核心不变量**（§6 / A14） | 只有真实执行产生的权威回执能驱动成功 |
| **一数一源** | 命令的最终状态归 transaction-service，步骤账不能自己当权威 |
| **可核对性** | 回执里的 `command_id` 与步骤自己的补偿命令 id **不是同一个** —— 照回执去查命令会查不到 |

**净效果**：`_p3_saga_view` 只看 `command_status == "SUCCEEDED"`，
于是"没派发"的补偿被算作完成，整单报 `COMPENSATED` ——
这正是"**看板说补偿完了，实际什么都没做**"。

### 为什么它此前没被发现

A08 的既有用例**走完了整条补偿路径并断言 `COMPENSATED`**——
它们断言的是"流程能走完"，而不是"成功是挣来的"。
伪造的回执让断言一路通过。

> **这又是一次"各环都绿、环之间没验"**：
> 这一环缺的判据不是"能不能走完"，而是"**走完的依据是不是真的**"。

## 二、核查：全仓只有这一处是伪造

审计所有 `authority_verified: True` 的出现处，共 4 处：

| 位置 | 函数 | 性质 |
| --- | --- | --- |
| L1642 | `_handler_p15_receipt` | **合法**——外部回执经接口送达 |
| L2259 | `_handler_p3_reconcile` | **合法**——收敛时记录源系统结论 |
| L2579 | `_p3_receipt` | **合成夹具**——构造 Saga **步骤账**，前提是被引用的命令已执行 |
| **L2949** | **`_handler_p3_saga_compensate`** | **伪造**——声称一次未派发的动作成功了 |

只有第 4 处是缺陷。第 3 处（`_p3_receipt`）是**测试场景的构造**，
不是"声称某个动作做过了"，性质不同，本轮**未改动**（保留在已知限制里）。

## 三、修法：让 `COMPENSATED` 是**挣来的**

三处改动：

### 1. 补偿命令变成**真实命令记录**

- `command_status` 改成 `AUTHORIZED`（**受理，不是成功**）；
- `authority_receipt` 置 `None`；
- 在命令存储里**登记真实的命令记录**（binding / 审批 / 版本），
  这样它能像其它命令一样取租约、执行、收敛。

> 旧实现只在步骤账里写了个 `command_id` 字符串，命令存储里根本没有它——
> 既不能执行，也无法核对。

### 2. 补偿需要**明确批准**（R2 语义）

补偿用的 `erp.inventory.reserve` 是 **R2**，`revalidate_before_execution`
会拒绝无批准的执行。**这是对的**：补偿会改动账务，不能因为"它是撤销"就自动获授权。

所以修法里同时写了一条**真实批准事实**（与 P0 决策接口写同一张 `approvals` 表），
批准人取 demo 审批人——**真实部署里它必须来自人**。

### 3. 判定依据从"自报状态"改成"**已验证的回执**"

新增 `_compensation_receipt_is_verified()`，要求**三条同时成立**：

1. `command_status == "SUCCEEDED"`；
2. 存在回执且 `authority_verified is True`；
3. **回执的 `command_id` 与补偿命令是同一个**（第 3 条直接对应上面那个 id 不一致的缺陷）。

### 4. 顺带修掉一个"永远达不到"的 bug

步骤账只在**补偿受理那一刻**记快照，而补偿命令随后的进展（租约 → 执行 → 回执）
全写在**命令**上，**不会回写步骤账**。

结果：即使补偿真的跑完并拿到权威回执，Saga 视图仍显示 `AUTHORIZED`、
`authority_receipt: None` ⇒ **`COMPENSATED` 永远达不到**，看板永远停在"处理中"。

修法：新增 `_compensation_live_state()`，把补偿的**实时**状态从命令存储投影进来
（步骤视图与汇总用同一份投影，避免同一响应里两处状态不一致）。

> 这是"一数一源"的直接推论：**命令的最终状态归 Transaction**，
> 步骤账只是编排投影。

## 四、测试随之升级：从"走完"到"挣到"

`test_saga_requires_physical_restore_before_accounting_compensation` 改造后：

1. 补偿受理时断言 `command_status == "AUTHORIZED"`、`authority_receipt is None`、
   整单 `!= "COMPENSATED"`；
2. 新增 helper `_drive_compensation_to_receipt()`——
   **真的**给补偿命令取租约、执行、收敛，收敛那一步才产生权威回执；
3. 两条补偿都跑完后，才断言 `all_compensation_receipts_verified is True` 与
   `COMPENSATED`。

**顺序断言一条没少**（实物先于账务、契约两域顺序、实物证据）。

新增 `tests/e2e/test_compensation_chain.py` 两条：
补偿不得预先声称成功且不得带回执；补偿必须登记**真实可读**的命令。

## 五、已知限制

1. **`_p3_receipt` 仍是合成夹具**：它给 Saga 的**步骤账**造回执，
   前提是"被引用的原命令已执行"。真实部署里这些回执应由原命令的实际执行产生。
   本轮**不改**它——它的语义是"构造场景"，不是"声称某动作做过了"——
   但这一点应当被知情。
2. **补偿的批准人是硬编码的 `user-approver`**：真实部署必须来自人
   （SSO 未接入，见 ADR-0004）。
3. **补偿命令没有真正派发到外部系统**：它走的是"取租约 → 执行 → 收敛"的受控路径，
   收敛时的源系统结论由调用方给出。**真实 MES/WMS/ERP 的派发与回执**属外部依赖。
4. **`object_phase` 固定为 `NOT_STARTED`**：真实补偿需要按对象当前阶段走分支
   （已发货/已过账要人工作业），当前分支逻辑在步骤账层判定。
