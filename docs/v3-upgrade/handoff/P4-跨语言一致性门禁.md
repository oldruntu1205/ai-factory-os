# 跨语言一致性门禁：抓到"重复撤销按钮"的真实缺陷

- 日期：2026-10-05
- 依据：上游 §12（发布状态机）、§17 A09
- 判据：`scripts/gate.py --stages p0,p1,p15,p2,p3,p4,assertions` **exit 0**（1345 用例）；
  变异 **149 个可捕获项全捕获**（p2 90、p3 29、p4 17、p15 7、p1 6）

---

## 一、背景：上一轮我明确记下的未加守卫

上一轮交付发布面板时，我在"已知限制"里写了：

> 七态顺序在服务端与前端**各写一份**（`RELEASE_STATES` vs `packages/domain/release.py`）。
> 前端那份只影响给不给按钮，不影响安全；但两份仍可能漂移——
> 当前靠"后端独立校验"兜底，**未加跨语言一致性守卫**。

本轮把这个守卫补上，**并立刻抓到一个真实缺陷**。

## 二、⚠️ 抓到的缺陷：`ACTIVE` 会出现两个"撤销"按钮

```
Python 七态: [DRAFT, SCHEMA_FROZEN, CALIBRATED, SHADOW, APPROVED, ACTIVE, REVOKED]
JS     七态: [DRAFT, SCHEMA_FROZEN, CALIBRATED, SHADOW, APPROVED, ACTIVE, REVOKED]

逐状态比对 legalNext（js vs domain）：
  OK DRAFT           js=['SCHEMA_FROZEN', 'REVOKED']  py=['SCHEMA_FROZEN', 'REVOKED']
  ...
  !! ACTIVE          js=['REVOKED', 'REVOKED']        py=['REVOKED']        ← 这里
  OK REVOKED         js=[]                            py=[]

结论：**两份实现已漂移**
```

**根因**：`ACTIVE` 的**下一个状态本来就是 `REVOKED`**，而 JS 又**无条件追加了一次终态**：

```javascript
if (index + 1 < RELEASE_STATES.length) next.push(RELEASE_STATES[index + 1]);
next.push(RELEASE_TERMINAL);        // ← ACTIVE 时与上一行重复
```

**后果**：界面上出现**两个"撤销"按钮**。

**严重性诚实评估**：**安全上无影响**——后端 `release_transition_allowed` 独立判据，
两个按钮都只会发出合法的 `ACTIVE → REVOKED`。但它是一个**真实的界面缺陷**：
用户看到两个一模一样的按钮，会怀疑其中一个有别的含义。

**修法**：前进一格恰好是终态时不再追加。

## 三、⚠️⚠️ 更值得记住的：**第一版核对器本身犯了这个错**

第一版核对器我在 Python 里**把 JS 的规则重算了一遍**再比对：

```python
def _js_legal_next(current):
    states = _js_states()
    ...
    if index + 1 < len(states): result.append(states[index + 1])
    result.append(terminal)          # ← 我照着 JS 又写了一遍同样的 bug
```

那不是核对，而是"**我读了一遍 JS、照着自己的理解又写了一份 Python**"。

**证据**：修好 JS 之后，核对器**仍然报漂移**——因为它比的是我的复算，
而不是真实实现。这个"修了还报错"的现象才让我发现核对器是假的。

**修法**：**用 `node` 真跑 JS 函数**——把 `legalNextStates` 源码从 `server.mjs`
裁出来、在 node 里执行、取回真实结果。

> **教训：核对器如果重写了被核对对象的逻辑，它核对的是自己的理解。**
> 这与本项目反复出现的"两套真相"是**同一个病**，只是这次病人是测试自己。

## 四、门禁实现

`tests/infra/test_cross_language_parity.py`（5 条）：

| 用例 | 断言 |
| --- | --- |
| 状态序列与终态一致 | 七态顺序、`REVOKED` 终态两侧相同 |
| **逐状态**合法下一步一致 | JS 给界面的按钮集合 == domain 判据集合 |
| **无重复项** | 对应本轮抓到的缺陷 |
| 终态不给按钮 | `REVOKED` 之后没有任何下一步 |
| **能力自检** | 内存里改 JS 一处，核对结果必须反映出来（证明它**真的在执行 JS**） |

第 5 条是本轮的核心：**没有它，第一版那种"复算型核对器"会长期绿灯**。

## 五、变异

新增 2 条（都是"漂移"这一缺陷类的两个方向）：

| 变异 | 结果 |
| --- | --- |
| **JS 侧**漂移（给出重复的终态按钮） | **捕获** |
| **Python 权威侧**漂移（顺序改为非相邻） | **捕获** |

验两个方向很重要：只验一侧，等于只证明了"JS 改动会被发现"，
而**权威侧改动**（更危险）无人看守。

## 六、已知限制

1. **只覆盖发布状态机**这一处跨语言判据。`apps/` 里其它"界面自算"的东西
   （如 `escapeHtml` 在页面与 `view.js` 各有一份）**未纳入**。
2. **核对器依赖 JS 函数的源码形状**（靠 `const RELEASE_STATES` 与
   `function legalNextStates` 定位裁片）。重构改名会让它报"找不到"而**不是**
   报"漂移"——这是可接受的失败模式（响亮地坏掉），但需要知道。
3. **不替代后端校验**：JS 那份始终只是"给不给按钮"，安全边界在 domain。
4. 本轮**没做对账页/员工页**（§15 仍缺）——插进来的这个缺陷优先级更高。
