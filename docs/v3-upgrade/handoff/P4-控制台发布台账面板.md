## 一、为什么做这个（结束连续多轮的"守卫"工作）

前 6 轮我一直在加内部守卫。本轮回到**功能面**，找出真正未做且**不依赖外部输入**的缺口。

按上游 §15，`apps/web-admin` 应有**员工／发布／对账**页——而我只做了状态面板。
其中**发布**最值得先做，因为它的状态机**已经实现、有测试，但控制台看不见**：

- 七态：`DRAFT → SCHEMA_FROZEN → CALIBRATED → SHADOW → APPROVED → ACTIVE → REVOKED`；
- 规则：**只能相邻推进一格**；非终态可**直接撤销**；`REVOKED` 是终态；
- 两条**恒定安全声明**：`ai_new_actions_enabled` 恒 `false`、`control_write_disabled` 恒 `true`。

## 二、做了什么

### 界面（新增「边缘发布台账」面板）

- 输入 `release_id` 查询；
- **时间轴**标出当前处于哪一格；
- **恒定安全声明照实显示**，并明确写"**不随状态推进放开**"
  —— 界面若把它们显示成已放开，就是在**替上游承诺**它没承诺的事；
- 推进区**只列出合法下一步**（相邻一格 + 撤销）。

### 服务端（`apps/web-admin/server.mjs`）

| 接口 | 作用 |
| --- | --- |
| `GET /api/v3/release?release_id=` | 读台账 + 计算 `legalNext` |
| `POST /api/v3/release-transition` | 推进一格（CAS） |

**安全边界在后端**：请求体里的 `to` 是客户端可改的，所以
`edge.release_transition_allowed` 会独立校验 `current → target`。
界面算错只会少给一个按钮，**不会让非法转换通过**。

## 三、端到端实测（真实链路，非单测）

| 场景 | 结果 |
| --- | --- |
| 查询 DRAFT 台账 | `legalNext = [SCHEMA_FROZEN, REVOKED]`；恒定声明 `false` / `true` |
| 相邻推进 `DRAFT → SCHEMA_FROZEN` | **200** |
| **跳态** `SCHEMA_FROZEN → SHADOW`（跳过 CALIBRATED） | **409 `EDGE_RELEASE_TRANSITION_NOT_ALLOWED`** |
| 非终态**直接撤销** → `REVOKED` | **200** |
| 终态再出发 | **409** |
| 推进后恒定声明 | 仍 `false` / `true`（**不随状态放开**） |

## 四、⚠️ 顺带修掉一个隐蔽的真实缺陷：硬编码的假 `task_id`

`resolveCommand` 里原本写死 `task_id: "task-demo"`。

**它不是真实任务** —— 只是恰好非空，用来绕过 `_p3_get_context` 的
「工厂只读链路要求 task_id 非空」。

**后果很隐蔽**：演示环境每次重启都会产生**新的** task_id，
于是读取接口返回 400，而界面只看到"读不到"，
**看不出是因为上下文里那个任务根本不存在**。

**修法（三层）**：

1. 新增 `resolveTaskId()`：优先读 `.v3-dev/demo.json`，否则**真建一条任务**；
   拿不到就**如实报 `NO_TASK_CONTEXT`**，而不是塞一个看着合理的假值；
2. `tools/v3_dev_cluster.py demo` 现在**同时创建并写出 `task_id`**；
3. 命令／批准／发布读取路径统一走 `resolveTaskId()`。

## 五、⚠️ 一条被**删除**的变异（诚实记录）

我为"`from` 不采信客户端"加过一条变异：

```
[逃逸] 发布转换的 from 采信客户端（可声称任意当前状态）
```

**诊断**：该函数**从不读取请求体的 `from`**，所以 `form.from ?? ...` 是**惰性的**——
在观测上不可区分（除非先改路由去接受该字段）。

**结论**：这里的安全性来自**路由不接受 `from` 字段**，
而不是来自某行判据。要让"采信客户端"成为可注入的缺陷，得先改路由，
而那本身就容易被评审看出来。

**处理**：**删除这条变异**（它测不出东西），并把这个判断**写进代码注释**
——免得下一个人再为它加一次无效变异。

> 这条不是"门禁有盲区"，而是"**变异本身是空转的**"。
> 区分这两者很重要：前者要修门禁，后者要修变异。

## 六、测试

`tests/web_admin/test_release_panel.py`（8 条）：

| 用例 | 断言 |
| --- | --- |
| 恒定声明 | `ai_new_actions_enabled=false`、`control_write_disabled=true`，**推进后仍是** |
| 相邻推进 | 200，`from`/`to` 如实回报 |
| **跳态被拒** | 409 `EDGE_RELEASE_TRANSITION_NOT_ALLOWED`，**且状态未被改动** |
| 多步跳跃被拒 | DRAFT 直接到 APPROVED 也不允许 |
| 非终态可直接撤销 | 200；撤销后 `isTerminal=true`、`legalNext=[]` |
| 终态不能再出发 | 409 |
| 撤销使批准失效 | `approval_current=false`、`approval_ref=null` |
| 读取不依赖假 task_id | 读取必须成功（不允许 400） |

### 一次测试自身的误报（修法值得记住）

第一版这组用例**直接打 `127.0.0.1:8300`**，并用 `skipif(_admin_reachable())` 守卫。
结果门禁里**一堆 ConnectionRefused**：

1. 守卫在**导入时**判定，而门禁会先杀掉控制台 ⇒ 判定"可达"、实际连不上 ⇒ **误报**；
2. 依赖"外部恰好有人在 8300 跑着"，在干净环境里**必然不可复现**。

**修法**：改为**自起控制台于随机端口**（与 `test_decision_write_path.py` 同构），
集群没跑就自起一套。修完后 **22 条 web_admin 用例全绿，且不依赖外部状态**。

> 教训：**测试对外部"恰好有服务在跑"的依赖，是误报的温床。**

## 七、已知限制

1. **只做了发布面板**：员工页、对账页仍未做（§15 要求）。
2. **`APPROVED` 路径未在界面走通**：带批准引用需要一份"当前有效"的批准，
   界面没有引导流程（只在代码里支持）。
3. **界面不做门禁的自查**：`ai_new_actions_enabled` / `control_write_disabled`
   是**读取**服务端字段并照实显示；界面**不会**（也不该）自己判断它们。
4. **七态顺序在服务端与前端各写一份**（`RELEASE_STATES` vs `packages/domain/release.py`）。
   前端那份**只影响给不给按钮**，不影响安全；但两份仍可能漂移——
   当前靠"后端独立校验"兜底，未加跨语言一致性守卫。
