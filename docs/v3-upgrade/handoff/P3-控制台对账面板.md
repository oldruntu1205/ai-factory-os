## 一、为什么做这一页

上游把 UNKNOWN 定为**必须查状态**的状态，并明确禁止两件事：

| 禁止 | 代码 |
| --- | --- |
| **换新键重发** | `RESEND_NEW_KEY` |
| **直接补偿** | `DIRECT_COMPENSATION` |

界面上「UNKNOWN = 结果未知，需对账」只是**一个标签**。而对账真正要给人看的是：
**查了没有、源系统怎么说、允许做什么、禁止做什么。**

没有这一页，运维看到 UNKNOWN 只能翻日志或直接打接口——
而**"禁止动作"恰恰最需要被看见**：它是防误操作的清单。

## 二、做了什么

控制台新增「UNKNOWN 对账（收敛记录）」面板（`GET /api/v3/reconciliation?command_id=`），
把收敛视图整理成三段**按重要性排序**：

| 顺序 | 内容 | 为什么要紧 |
| --- | --- | --- |
| ① | **禁止动作清单**（最显眼，红框） | 防误操作；上游定成恒定输出正是为了让验收能断言"它一直在" |
| ② | 候选动作 | 允许做什么 |
| ③ | 重试约束（同一幂等键 + 必须重新走执行前复核） | 复用旧批准结论被明确禁止 |

另有"是否查证过源系统"一栏：**没查证过的结论不能当依据**。

## 三、⚠️ 一个设计判断：「没有收敛记录」不是错误

后端对没有 `reconciliation_ref` 的命令返回 **404 `RECONCILIATION_NOT_FOUND`**
（"该命令尚无收敛记录"）。

那表示**"尚未进入 UNKNOWN 收敛"，不是失败**。所以控制台把它如实呈现为**一种状态**：

> **尚未进入对账。** 该命令没有收敛记录（后端 `RECONCILIATION_NOT_FOUND`）。
> 这说明它还**没有**因为超时／失联而进入 UNKNOWN 收敛。

若把它当错误弹红，运维会去查一个**本来就不该有记录**的命令——
**把正常状态报成异常，比不报更糟**。

## 四、端到端实测（真实链路）

用演示命令查（该命令走过标准收敛路径）：

```
源系统结论 = SUCCEEDED        查证次数 = 1        是否查证过 = 是
候选动作   = [MANUAL_REVIEW]
禁止动作   = [RESEND_NEW_KEY, DIRECT_COMPENSATION]
重试键     = null（已成功，不给键）        必须重新走复核 = 是
```

**注意 `retryKey = null`**：命令已 `SUCCEEDED`，**不给重试键**是对的——
给了会诱导重复副作用。这条也写进了门禁。

## 五、门禁（6 条）

`tests/web_admin/test_reconciliation_panel.py`：

| 用例 | 断言 |
| --- | --- |
| **禁止动作清单必须一直在** | 具体断言 `RESEND_NEW_KEY`、`DIRECT_COMPENSATION` 两项 |
| 源结论与是否查证过如实转达 | `NOT_EXECUTED` + `queryVerified=true` + 次数 ≥ 1 |
| 重试约束 | `retryNeedsFreshReview=true`；`CONFIRMED_NOT_EXECUTED ⇒ RETRY_SAME_KEY` 且**给出同一键** |
| **已成功不给重试键** | 防"诱导重复副作用" |
| **没有记录 = 状态不是错误** | 200 + `noRecord`，且带后端原因码 |
| 缺 `command_id` 明确拒绝 | 400 `MISSING_PARAM`，不猜一个 |

测试**自起控制台于随机端口**（沿用上一轮教训：不依赖外部恰好有服务在跑）。

## 七、已知限制

1. **只做只读**：这一页**不提供**触发收敛或重试的按钮。这是刻意的——
   重试会重新产生副作用，应走既有的受控命令路径，而不是在一个"查询页"上点一下。
2. **重试的完整闭环未在界面走通**：`RETRY_SAME_KEY` 只显示约束与键，
   界面不代发重试请求。
3. **仍缺员工页**（§15 三项里最后一项）。员工数据（`registry.mock.json` 的
   `employees`）**没有对应路由**，需要先加内核接口——属于契约面改动，未纳入本轮。
4. **`edge/` 独立部署树仍未建**（ADR-0006 有意延后，待 P5 现场许可）。
5. **任务↔命令关联**仍是如实登记的缺口（`command_refs` 全仓无写入路径）。

## 八、⚠️ 一条被**删除**的变异，以及纠正我自己写错的断言

我为 `queryVerified: view.query_verified ?? null → true` 加过一条变异，它**逃逸**了。
我先写了"源结论 `UNKNOWN` ⇒ `queryVerified` 应为 `false`"的用例去抓它，**用例失败了**。

查代码后确认：**是我的断言错了，不是实现错了**。

```python
# 前置校验：非集合值直接 400
if source_state not in transactions.SOURCE_STATES:
    raise errors.reject_bad_request("source_state", "源系统结论不在允许集合内")
...
"query_verified": source_state in transactions.SOURCE_STATES,   # 恒为 True
```

而 `SOURCE_STATES = ("SUCCEEDED", "NOT_EXECUTED", "UNKNOWN", "FAILED", "accepted")`
——**`UNKNOWN` 本身就在集合里**。所以任何**可达**的记录都有 `query_verified = true`。

**结论**：那条变异是**空转的**（改动在可达输入上不可区分），**不是门禁有盲区**。

**处理**：删除该变异；把用例改成**记录这个实测出来的不变量**
（`UNKNOWN` 表示"已查证，但结论未知"，所以 `queryVerified` 为 `true`）；
并注明界面里"否（结论不可当依据）"那句是**不可达分支**（防御性代码，留着无害）。

> **区分"门禁有盲区"与"变异空转"很重要：前者要补测试，后者要删变异。**
> 这与第 31 轮那条 `from` 不采信客户端的变异是**同一类**。
