# 共享领域包（`packages/domain/`）

- 日期：2026-10-05
- 依据：上游 §15「`packages/domain/` —— 纯领域类型/约束，**不依赖服务 DB 或运行时**」；
  §15 同时规定「共享包只共享契约和纯函数，不共享业务 repository、数据库连接或服务私有模型」
- 判据：`scripts/gate.py --stages p2` **exit 0**；变异 `--phase p2` = **36/36 可捕获项全捕获**

## 1. 这个包存在的理由（不是"为了符合布局"）

有一类知识是**中心与现场必须逐字一致**的：

- Guard 的判定阶段与它们的**优先级顺序**；
- 判定原因码 → 阶段的归属；
- 哪些原因码要求安全回退；
- 边缘发布的 7 状态机与允许的迁移。

这类知识一旦在两处各写一份，就会出现"同一语义两套术语"——
接口对接时必须翻译一次，**而翻译就会出错**。

## 2. 这不是假想的风险：项目里已经有一份手抄

审计发现：

| 位置 | 内容 |
| --- | --- |
| `services/_kernel/edge.py` | `GUARD_STAGES`（9 个阶段）+ `REASONS_REQUIRING_FALLBACK` |
| `services/_kernel/metrics.py` | **手抄的**阶段名 + **22 条**原因码映射 + `unknown` 桶 |

而 `edge.py` 里真实产出的原因码有 **22 个**——两份之间**没有任何机制保证一致**。

失效方式很隐蔽：`edge.py` 新增一个原因码时，指标侧**不会报错**，
只会把它静默归进 `unknown` 桶。于是某个阶段的拒绝率**长期偏低**，而没人会发现。

## 3. 做法：阶段表由原因码映射**派生**，不另写一份名单

```
GUARD_REASON_TO_STAGE   ← 唯一真相源（22 条原因码 → 阶段）
        │
        ├──► GUARD_STAGES = 映射里出现过的阶段（**派生**，不是手写）
        │
        └──► metrics.STAGE_LABELS = GUARD_STAGES + ("unknown",)
```

`GUARD_STAGE_ORDER`（顺序）单独声明——**顺序是上游的硬要求**，
不是按字母排的，无法从映射推出来。门禁断言它与契约 `p4-guard.json`
的 `Check.stage` 枚举**逐字且同序**一致。

`unknown` 桶保留在**观测侧**：指标需要一个"未识别"落点，
否则遇到未登记原因码会让整个指标计算抛错（把观测能力打挂）。
这与**现场判定阶段**是两回事——现场那 9 个阶段必须与契约逐字一致。

## 4. 漂移探针：让"两份词表分叉"变成机械可检

`metrics.unregistered_reason_codes_from_implementation()` 从 `edge.py` 源码里
抓出所有 `failures.append((stage, "CODE:..."))` 形状的原因码，逐个问 domain 认不认识。

门禁断言它为空——**漏登记即报红**，而不是静默归桶。

### 这条探针自己也需要自证（否则又是"假绿"）

第一版只有一条"实现里的原因码都已登记"的断言。变异测试指出：
把它改成恒返回空列表，门禁**照样全绿**——因为干净树上
"没有未登记码"与"根本不会识别未登记码"**在观测上无法区分**。

这正是本项目在仓库卫生守卫上踩过的同一个坑。补两条自检：

| 自检 | 断言 |
| --- | --- |
| 能力自检 | 喂构造输入 `["SOME_FUTURE_CODE", "ANOTHER_FUTURE_CODE:detail", "DRIFT_EXCEEDED"]` ⇒ **正好**报出前两个（已登记的不许出现） |
| 反向自检 | 喂全部已登记的原因码 ⇒ 报 0 条 |

手工注入验证也做过：在 `edge.py` 里插入 `SOME_FUTURE_CODE`，门禁立刻报红；
还原即恢复绿。

## 5. 交付内容

```
packages/domain/
├── guard.py            阶段/顺序/原因码映射/回退集合 + 纯函数查询
├── release.py          7 状态机与相邻推进规则
└── behavior_change.py  行为性变化类别与所需阶段
tests/domain/test_domain_purity.py   34 条用例
```

`services/_kernel/edge.py` 与 `metrics.py` 已改为**导入**而非复制。
`edge.py` 保留再导出，既有调用方与测试不受影响（行为逐字未变，已实测）。

## 6. 门禁覆盖

| 类别 | 断言 |
| --- | --- |
| 词表自洽 | 映射的每个阶段都已声明；每个阶段都有原因码归属；无重复 |
| **契约对齐** | 阶段名与**顺序**与 `p4-guard.json` 逐字一致 |
| 顺序语义 | `confidence` 必须最后（不能覆盖硬判定）；`highest_priority_stage` 按硬顺序 |
| 漂移探针 | 实现里的原因码全部已登记 + 两条能力自检 |
| 唯一来源 | `metrics._REASON_TO_STAGE`、`edge.GUARD_STAGES` 与 domain **对象相等** |
| 状态机 | 只允许相邻推进；`REVOKED` 终态且可从任意非终态直接撤销；未知状态拒绝 |
| 行为性变化 | 每类都有所需阶段；阶段必须是已声明状态；取**最早**那个；非行为性不使批准失效 |
| **纯函数性** | 用 AST 检查 imports（禁 `os`/`json`/`pathlib`/`sqlite3`/网络/`services`），并断言模块可在无仓库状态、无环境变量下导入 |

## 7. 已知限制

1. **只搬了 Edge 相关的领域约束**。数据分级（C0–C4）、风险等级（R0–R3）、
   金额与计量单位等仍在 `services/_kernel/` 内——它们尚未出现"两处各写一份"的问题，
   **没有重复就不搬**（搬动会扩大回归面而无收益）。
2. **纯函数性靠 AST + 导入检查**，不是形式化证明。
3. 契约对齐只覆盖 `p4-guard.json` 的 `Check.stage`；
   其它契约里若有同类枚举，尚未纳入这条断言。
4. `packages/domain` 目前被 `services/_kernel/` 单向依赖；
   若将来 Edge 侧独立部署，需确认打包方式能带上本包
   （上游要求 Edge 优先 Python，但真实打包方式待冻结）。
