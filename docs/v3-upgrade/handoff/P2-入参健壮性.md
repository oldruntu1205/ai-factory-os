# 入参健壮性 · 缺字段不得报成服务故障

- 日期：2026-10-05
- 判据：`scripts/gate.py --stages p2` **exit 0**；变异 `--phase p2` = **24/24 可捕获项全捕获**

## 1. 问题：把调用方的错误报成服务故障

起因是一次**我自己的误用**：用错了 `/internal/v1/commands` 的请求形状，
结果拿到 **`503 INTERNAL_ERROR`** 而不是 4xx。

顺着查下去发现这不是个例。该 handler 直接取 `body["command_type"]`，
字段缺失时抛 `KeyError`，被 dispatch 的兜底分支转成 `503`。

**为什么这是个真问题**：

| 报 503 的后果 | 说明 |
| --- | --- |
| 调用方以为服务坏了 | 触发重试、熔断、甚至告警——而真正的修法是改请求 |
| 排障方向被带偏 | 有人会去查服务日志、查依赖，而不是查自己发的请求 |
| 契约失信 | 这些端点的 OpenAPI 响应里**本来就声明了 400** |

## 2. 覆盖面：不是 1 个端点，是 33 个

我先试了**静态审计**（正则找 `body[...]` 再比对契约必填字段）——
结论是**噪声太大、不可靠**，放弃了：

- 路径参数（`{approval_id}`）会被误判为请求体字段；
- 契约的 `required` 语义与"这个入口是否由调用方提供该字段"并不一致
  （`payload_version` 在契约里是必填，但编排链路里由上游产出，调用方本就不填）。

改用**行为不变量**：对每个 POST 端点发一个
「公共 Context 齐备、但业务字段全缺」的请求体，断言**永不返回 5xx**。

实测：**33 个端点**返回 `503 INTERNAL_ERROR`。它们都是同一个形状——
handler 直接下标取字段，缺字段即 `KeyError`。

## 3. 修法：在内核兜底处判一次，而不是改 33 个 handler

逐个改 handler 是重复劳动，而且**下一个新 handler 还会再犯**。
正确的位置是 dispatch 的兜底分支：把「缺请求字段」识别出来，改报 **400**。

### 关键难点：判据不能太宽

如果简单地把"所有 `KeyError`"都转成 400，会**掩盖真正的内部缺陷**：
一个内部字典取错键的编程错误，会伪装成"客户端请求不合法"，
从此没人发现。

所以判据必须是「**这个名字确实是客户端该提供的请求字段**」：

| 类别 | 判定 | 理由 |
| --- | --- | --- |
| 公共 Context 的键（`CONTEXT_KEYS`） | ✅ 请求字段 | 平铺或嵌在 `context` 下都是客户端提供的 |
| 路径参数（`path_params`） | ✅ 请求字段 | 例如 `{command_id}`，由 URL 提供 |
| **该路由契约声明的请求体属性名** | ✅ 请求字段 | 契约是唯一权威 |
| 其它（如 `model_version`、`record_version`） | ❌ 走 503 | 这些是内部记录/登记的键，缺了就是代码缺陷 |

第 3 条让"这个字段本来就是给客户端填的"**可机械判定**，
而不是靠"名字像标识符"这种弱条件（`isidentifier()` 对
`internal_registry_key` 同样为真，等于没判——这一点被变异测试当场抓出）。

**读契约而不是维护名单**：代码里维护一份"哪些字段必填"的名单极易与契约漂移，
所以直接解析 `packages/contracts/openapi/*.openapi.json`。

## 4. 实现契约解析时踩的三个坑（都值得记）

### ① 多份 spec 不能共用一棵 `components` 树

每个 `*.openapi.json` 自带 `components`。第一版把各 spec 的 `components`
合并成一份，同名 schema 互相覆盖，`$ref` 解析到了别的 spec 的同名节点
（`TaskCreateRequest` 解析出 **0 个属性**）。

→ 改成**记住每条路径来自哪份 spec**，解析 `$ref` 时回到它自己那棵树。

### ② 外链 `$ref` 带 JSON Pointer 片段

`{"$ref": "../schemas/api-models.json#/$defs/TaskCreateRequest"}` ——
我只处理了文件路径、丢掉了 `#/$defs/...` 片段，于是永远取不到定义。

→ 补 `_walk_pointer()`，支持 `#/components/schemas/X` 与 `#/$defs/Y`。

### ③ 带真实 id 的路径匹配不上契约模板

请求路径是 `/releases/probe-release_id/gate-reopen`，契约里是
`/releases/{release_id}/gate-reopen`。第一版把非 `{...}` 的段一律当字面量，
于是 `probe-release_id` 永远匹配不上 `{release_id}`——**兜底判定整体失效**。

→ 归一化**必须问契约**："这一段的字面值有没有在任何模板的同一位置出现过"：
出现过就是字面段，没出现就是参数段。

## 5. 我在这轮里犯的两次错（记录以免重犯）

1. **过度收紧**：给 `/internal/v1/commands` 加必填校验时，把
   `payload_version` / `payload_hash` 也算必填——它们由上游编排产出，
   调用方本就不填，结果把 P0/P1.5 的建命令用例打红一片。
   → **「契约里是必填」≠「这个入口必须由调用方提供」**。
2. **测试自身写错**：第一版用空 body 发请求，端点在缺 Context 时**正确地**
   返回 400「公共 Context 的键必须全部显式提供」，我的断言却按"业务字段校验"
   去读消息，于是 49 条误报。→ 必须先附完整 Context，才能考到业务字段那一段。

## 6. 边界与遗留

- **只覆盖"缺字段"这一类**。语义错误（值不合法、状态冲突）由各阶段套件负责。
- **空体不是全字段覆盖**，它精确命中"缺字段即崩"。
- 契约解析失败（读不到 spec / 匹配不到路径）时返回空集 ⇒ 走 503 兜底。
  **宁可让真缺陷以 503 暴露，也不要猜测后掩盖**。
- 6 个豁免端点（查询/触发类 POST）写明理由，只要求"不崩"不强求"拒绝"。
- `/api/v1/tasks` 等端点用**同一份** Context 平铺 + 嵌套两种承载，是为兼容
  P0（平铺）与 P1（嵌套）两套契约写法，不是冗余。
