## 2. 最关键的设计：清单与代码**机械核对**，而不是各写一份

上游要求「端口、环境变量和依赖版本归部署 manifest 管理」。
但如果清单只是文档，它一定会与代码漂移——**端口写错、owner 对不上
这类问题在部署时才暴露**，那时排查成本最高。

所以 `manifest.yml` 是**给机器读的**，门禁逐项对照代码：

| 清单字段 | 对照代码 |
| --- | --- |
| `id` | `tests/p0_runtime/conftest.SERVICE_MODULES` |
| `module` | 同上（实际启动的 `-m` 参数） |
| `port` | `service_ports()` 的默认端口 |
| `port_env` | 命名规则 `V3_PORT_<ID 大写、连字符换下划线>` |
| `owner` | `services/_kernel/routes.OWNER_BY_SERVICE`（一数一源） |

漏一个、多一个、写错一个都报红。实测 6 条相关变异全部被捕获。

## 3. 网络按上游的域边界切，而不是"一个扁平内网"

| 域 | 用途 | 出网 |
| --- | --- | --- |
| `frontdoor` | 对外（`/api/v1/**`） | 允许 |
| `internal` | 服务间（`/internal/v1/**`） | **禁止**（`internal: true`，容器层面无默认网关） |
| `edge-uplink` | 中心 ← Edge 受控上行（`/edge/v1/**`） | **禁止** |

`edge-uplink` 单独成域的理由：Edge 会**断连**（上游 §8.3），
恢复后补报事实——它不能与普通内网共享"长连接"假设。

门禁断言的三类结构性风险：

1. **内部接口不得从对外的 `frontdoor` 域可达** —— 否则服务接口暴露给用户；
2. **内部服务不得直连外网** —— 否则绕过出域治理与审计；
3. **现场侧不得直调中心内部接口** —— 必须先上行到 `/edge/v1`。

另有：出域只允许 `security-gateway` 一个来源，且 `denied_by_default: true`。

## 4. 编排里"不给 shell 插入机会"，也不给弱默认值

- `ENTRYPOINT ["python"]` + compose 的 exec 形式 `command: ["-m", "..."]`：
  **不用 shell 形式**，避免 `$VAR` 在容器里被意外展开成空值；
- 端口一律 `${V3_PORT_XXX:-默认}`，默认值与代码一致；
- **凭据类变量禁止非空默认值** —— 门禁断言：`${SECRET_KEY:-devsecret}` 这种
  写法会报红。

> 一个非空默认值会让"忘记注入密钥"变成"悄悄用弱凭据跑起来"。

镜像细节：非 root（uid 10001）、依赖清单前置（改代码不重建依赖层）、
健康检查打契约登记的 `/health/live`。

## 5. 顺带完成的凭据审计（本轮发现，需要你决策）

审计仓库里的凭据文件时发现 **`deploy/prod.env` 被 git 跟踪**，
而它含有 `SECRET_KEY`、`LLM_API_KEY`、`WECOM_SECRET`、`SMTP_PASSWORD` 等键。

**定性（未打印任何值，用判定式分类）**：

| 键 | 长度 | 判定 |
| --- | --- | --- |
| `SECRET_KEY` | 39 | 低熵、三段纯英文词 ⇒ **开发占位符** |
| `LLM_API_KEY` | 23 | 含提示词 "key" ⇒ 占位符 |
| `WHATSAPP_VERIFY_TOKEN` | 12 | 低熵、两段英文词 ⇒ 占位符 |
| `FIREWORKS_API_KEY` / `WECOM_SECRET` / `SMTP_PASSWORD` 等 | 0 | 空 |

**结论：当前没有真实机密泄露**（唯一字符数 32/39 且为自然语言，非高熵随机串）。

**但风险是结构性的**：该文件被跟踪且含 `SMTP_PASSWORD` 这类键，
一旦有人把真值填进去，下一次提交就会泄露。`.gitignore` 里虽有 `**/.env`，
但**已被跟踪的文件不受 ignore 影响**。

**处置建议（未执行，等你确认）**：

1. `git rm --cached deploy/prod.env`（**保留磁盘文件**，只取消跟踪）；
2. 补 `deploy/prod.env.example`（只含键名与说明）；
3. 若希望彻底不留在历史里，需 `git filter-repo`/BFG 重写历史 ——
   这一步**必须你明确授权**，因为它改写提交、影响协作者。

另：仓库根 `docker-compose.yml`（V2.1 遗留）含硬编码口令 `industrial123`。
门禁里有一条用例**显式登记它的存在**，避免它被误当成 V3 编排；
修正它属单独一步。

## 6. 已知限制

1. **`frozen: false`**：清单与 ACL 都显式列出阻塞项（生产库、密钥管理、
   身份与批准岗位、运维参数、外部组件适配）。未冻结前不声明为已定。
2. **没有真实跑过 `docker compose up`** —— 本机无 docker。
   编排文件经过 YAML 解析与结构断言，**不等于容器真的能起来**。
   这点必须如实标注：一个"看起来对"的 compose 与"验证过能起"的 compose
   是两回事。
3. **ACL 是声明，不是强制**：真正生效需要网络层（安全组/iptables）
   按本文件落地；应用层仍独立做数据分级判定，避免两处口径漂移。
4. **只覆盖本地开发编排**；生产编排（含真实密钥注入通道、TLS、
   反向代理）待外部依赖冻结。
5. `Dockerfile.service` 依赖 `backend/requirements.txt`；若该文件被
   拆分为多份，需同步更新。
