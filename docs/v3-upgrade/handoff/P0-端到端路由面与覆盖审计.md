- 判据：`scripts/gate.py --stages p0,p1,p15,p2,p3,p4,assertions` **exit 0**（1217 用例）；
  变异 **118 个可捕获项全捕获**

## 一、先说方法上的教训：文本探针**不可靠**

我想知道"某条接口到底有没有被测试真的调用过"。第一版做法是 grep 测试代码里有没有出现该路径。

结果**同一件事得到了三个互相矛盾的答案**：

| 探针版本 | 结论 |
| --- | --- |
| 朴素子串匹配 | 5 条未覆盖 |
| 归一化占位符后 | 8 条未覆盖 |
| 再处理 f-string 片段后 | 又是另一组 |

原因很实在：测试用 **f-string 拼路径**（`f"/internal/v1/edge/releases/{id}/transitions"`）、
把前缀拆成常量、路径用 `$` 转义。文本匹配既会**漏**（拼出来的路径 grep 不到）
也会**误报**（注释里提一句就算命中）。

**所以改为在真实 dispatch 上记账。**

## 二、运行时取证：把"被调用过"变成事实

在 `services/_kernel/http.py` 的 `dispatch` 里，**路由匹配成功之后、认证之前**加一行记账：

```python
coverage_file = os.environ.get("V3_ROUTE_COVERAGE_FILE")
if coverage_file:
    with open(coverage_file, "a", encoding="utf-8") as handle:
        handle.write(f"{request.method} {route.pattern}\n")
```

三个设计点：

1. **默认关闭**——不设环境变量时零开销，不污染正常运行；
2. **记账在认证之前**——覆盖关心"这条路径可达"，而认证失败（越权用例）也是真实调用；
3. **记账失败绝不影响业务请求**（`except OSError: pass`）。

设了变量后跑完全部 1140 条用例，得到**事实**：

```
注册路由: 61   实测被调用过的不同路由: 60
从未被调用: GET /api/v1/edge/shadow-reports/{report_id}
```

## 三、缺口：一条"已接线却零覆盖"的接口

`GET /api/v1/edge/shadow-reports/{report_id}` 已注册、已声明"接口已接线"，
但**从来没有被任何用例调过**。

它是不是坏的？**之前不知道**——这正是问题：

> 接口接线了却零覆盖，要么它是**死代码**，要么它**坏着而没人发现**。两种都不该存在。

它可直接测试：与 `POST /edge/v1/shadow-reports` **共用同一个 journal**（`edge-shadow-reports`），
所以能真的造出一份报告再读回来，**零外部依赖**。

补的三条（拆到 `tests/e2e/test_shadow_report_read.py`）：

| 用例 | 断言 | 内容 |
| --- | --- | --- |
| 读回一致 | A09 | 冻结门槛 → 登记报告 → 读回；6 个字段 + `threshold_ref`/`threshold_hash` 逐字一致 |
| 缺失明确 404 | A09 | 不得返回空对象伪装成"有但空"；错误码必须是 `SHADOW_REPORT_NOT_FOUND` |
| 跨租户不可见 | **A01** | 另一租户读到的必须与"不存在"**无法区分**（否则存在性成侧信道） |

写这些用例时踩到两个真实约束（都由 handler 实现决定，不是猜的）：

- 报告**必须引用已冻结门槛**（§9 不接受报告自带标准）⇒ 必须先走一遍 `thresholds/freeze`；
- **`report_id` 由服务端生成**，请求体里的值被忽略 ⇒ 要拿响应里的 id。

## 四、门禁：全路由可达性（`test_route_reachability.py`）

对**每条注册路由**发一次请求，断言它**确实路由到了处理器**：

- 不得"路径不属于本服务"（那意味着打不到）；
- 不得 400 且理由为"方法不匹配"（方法登记错了）；
- **业务对象不存在不算失败**——请求走到了处理器、按业务规则回答了，可达性成立；
  但必须给出**明确的业务错误码**，不能是空壳 404。

外加一条**探针自检**：收集函数必须覆盖全部注册路由。
没有它，"全路由可达"这句话本身可能就是残缺的——少列几条，测试照样全绿。

> 这条断言的价值：**新增路由却忘了接测试时会立刻报红**，
> 不需要谁记得更新覆盖清单（清单本身会过期）。

**复测结果：注册 61 条，实测被调用 61 条，零覆盖 = 0。**

## 五、顺带澄清一个我起初误判的问题

审计时发现 `ROUTES_BY_OWNER` 有 **9 个 owner** 但只有 **8 个 service**，
且有若干"同方法+同路径"重复注册，我一度怀疑是路由遮蔽缺陷。

核实后：两种情况**都已由 V3 自己处理**：

- `edge` owner 无对应 service，但 `routes_for()` 显式把它并入 `manufacturing-core`
  （`EDGE_OWNER_SERVICE`，本地验证用；生产由 Edge Gateway 承载）；
- 重复的 `POST /internal/v1/events` 等是**跨服务各注册一份**——
  每个服务要有自己的路由表，这是设计，不是重复；
- 已有 `test_route_registry_has_no_duplicate_owner_keys` 守住 owner 键唯一。

**教训：看起来像缺陷的东西，先确认它是不是已被别名机制/既有测试覆盖。**

## 六、已知限制

1. **可达性 ≠ 业务语义**：这条只证明"能调到"。语义由各阶段套件负责，
   这也是为什么补了 §3 那三条真语义用例，而不是止步于可达。
2. **取证依赖环境变量**：忘记设 `V3_ROUTE_COVERAGE_FILE` 就不会记账，
   所以它**不是** CI 自动门禁，而是**审计工具**。真正的防线是
   `test_route_reachability.py`（它不依赖记账，每次都真发请求）。
3. **记账只到路由粒度**：同一路由的不同分支仍可能没被覆盖。
4. **`tests/e2e` 目前只有"路由面 + 影子报告读"**；
   跨阶段全链路（任务→批准→命令→回执）仍是各阶段分别验的。
5. `tests/e2e/test_route_reachability.py` 作为**结构约束**登记在
   `UNTAGGED_SUITES`（不映射 A01–A14）；同目录的业务用例**已带** A01/A09 标签。
