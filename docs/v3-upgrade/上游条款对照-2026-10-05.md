## 0. 为什么会有这份文档

此前本仓对上游的核对方式是**按需 grep + 定点读**：带着具体问题去搜关键词。
那种方式有个结构性缺陷——**它只能发现"我去找过的东西"**。

一个真实例子：员工数据模型（岗位/限额/权限）此前**整块不存在**，
是因为某轮恰好去 `grep` 了它才被发现；若没搜到，它会一直是洞，
而交接文档会继续写"员工页未做，缺个路由"（那句不准确的话写了好几轮）。

本文把"我读过上游"这件事变成**可机读、可重跑的逐条对照**。

## 3. 本轮修复

### 3.1 `_handler_policy_evaluate` 的死分支（真实缺陷）

修复前：

```python
"reason_code": "reason-demo" if allowed else "reason-demo",
```

两个问题：

1. **两个分支同一个值**——等于没有区分，却长得像区分了；
2. `reason-demo` 属于 `decision_catalog`，是**另一类决策**的目录。
   契约把 `reason_code` 声明为 `CatalogValue`（`x-catalog-required: true`），
   策略判定借用它，会让审计分不清一条原因码出自哪类判定，
   也会让一边扩目录时意外放宽另一边。

修复后：

- `registry.mock.json` 的 `policy-demo` 新增 **`reason_codes`** 目录
  （`allowed` / `approval_required` / `denied` 三值）；
- `registry.py` 新增 `policy_reason_codes()`，**只从策略自己的目录取**；
- **目录缺失 ⇒ fail-closed 拒绝**（不给"默认原因码"——编一个出来，
  审计会看到一句目录里并不存在的判定依据）；
- `tests/transactions/test_policy_reason_codes.py` 钉住：三类情形原因码互不相同、
  全部在目录内登记、策略目录与决策目录**不共用值**。

> **未覆盖的诚实标注**：`denied` 分支在当前 `policy-demo` 下**不可达**
> （没有哪条规则同时 `auto_execute=false` 且 `requires_approval=false`），
> 因此测试**不假装覆盖它**——目录里为它留了原因码，等真有规则时再验。

### 3.2 新增测试（23 条）

| 套件 | 条数 | 覆盖 |

| `tests/isolation/test_cross_tenant_boundary.py` | 3 | A01：别租户 task 读不到（**先证明本租户读得到**，避免假绿）；不存在的 command 在两租户下回答同构（不泄露存在性）；未登记租户在控制面与决策面都 fail-closed |

**两条值得单说的判据设计**：

- **基线放行**：`test_baseline_command_is_allowed` 先证明"什么都不改是放行的"。

- **跨租户响应同构**：不只要求"读不到"，还要求**两个租户对同一不存在记录的错误码一致**。
  否则响应差异本身成了探测器，可用来枚举别租户有没有该条记录。
