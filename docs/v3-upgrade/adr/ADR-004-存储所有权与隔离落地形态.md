# ADR-004：存储所有权与隔离的落地形态（PostgreSQL）

- 状态：**已采纳**（2026-10-05）
- 上游依据：§13（数据存储与所有权，其中 schema/role 隔离、禁止跨 owner 写表/join/外键、
  tenant 进隔离域为**硬要求**；PostgreSQL 为**建议基线**）
- 影响范围：所有 owner 的迁移与运行时数据访问

## 背景

§13 把多数选型列为"建议基线"，但以下四项是**硬要求**：

1. 每服务独立 schema + 独立 DB role，生产不使用超级用户；
2. **严禁**跨 owner 直接写表、跨服务 join、跨 owner 外键；
3. 所有业务主键、唯一索引、幂等域**必须包含 tenant**；
4. **RLS 作第二道隔离**，应用层身份检查仍为必须。

当前实现（P0–P1.5）用进程内内存 + JSONL journal 模拟，**这四项一条都没落地**。
问题在于：这类要求最容易在实现中被悄悄破坏（加个跨 schema 的 JOIN、给应用角色
补个 GRANT、新建表忘了 tenant），而**代码 review 很难稳定拦住**。

## 决策

1. **DDL 由代码生成，隔离不变量做成门禁断言**。
   新增 `services/_kernel/storage.py`：按 owner 生成 schema / role / 表 / RLS / 授权，
   并暴露可机检的不变量函数（`cross_owner_grants` / `tenant_scoped_tables_missing_tenant` /
   `tables_without_rls` / `roles_with_excessive_privileges` / `foreign_keys_across_owners`）。
   门禁 `tests/p2_storage` 断言这些不变量成立——**不需要数据库**。

2. **隔离靠"谁都不给别人权限"实现**，不是"给了再限制"。
   生成器**不产生**任何跨 owner 的 GRANT；同时显式 `REVOKE ALL ... FROM PUBLIC`
   （避免"新建 schema 默认全局可读"）。

3. **role 命名**：`{owner}_owner`（NOLOGIN，对象所有者）与 `{owner}_app`（LOGIN，运行时）。
   两者都 `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION`，应用角色 `BYPASSRLS OFF`。

4. **RLS 用 `ENABLE` + `FORCE` 成对开启**，策略读 `current_setting('app.tenant_id')`。
   FORCE 是关键：它让**表所有者也不能绕过** RLS，否则"owner 角色"会变成后门。

5. **全局表必须显式登记**。`tools.tool_specs` 是全局目录（非租户数据），
   在 `GLOBAL_TABLES` 里显式豁免，而不是靠"忘了加 tenant_id"。
   登记键用 `owner.table`（**schema 名与 owner 名不同**，如 owner `tools` 的 schema 是
   `tool-gateway`；用 schema 名当键会永远匹配不上——实现时踩过）。

## 被否决的替代方案

| 方案 | 否决理由 |
| --- | --- |
| 每 owner 一个独立数据库实例 | 运维成本与备份复杂度陡增；schema+role 已能提供同等隔离，且 `§13` 也只要求 schema |
| 用应用层 `WHERE tenant_id` 代替 RLS | §13 明确要求 RLS 作为**第二道**隔离，应用层检查不可替代 |
| 把隔离检查写成人工 Review 清单 | 这类要求靠 review 拦不住，必须可执行断言；且回归时会静默失效 |
| 直接在目标库跑 DDL 验证 | 目标 PG 实例属外部依赖，**待冻结**；把不变量与执行解耦才能进 CI |

## 后果

**正面**
- §13 的四条硬要求从"文档承诺"变成"门禁断言"，且不需要数据库。
- 新增 owner/表时，漏加 tenant 或漏开 RLS 会**直接让门禁报红**。
- 权限判定刻意写成"识别 ON/OFF 形态"而不是朴素子串（`NOSUPERUSER`、`BYPASSRLS OFF`
  都是正确形态），并有防回归用例——避免把健康 DDL 误判为过度权限。

**负面 / 需要管理**
- DDL 生成器与实际执行的 DDL 可能漂移。缓解：`generate_owner_ddl` 是唯一产出点，
  执行时直接落盘该文本；执行脚本待目标环境冻结后补。
- `OWNER_TABLES` 是一份**手工维护的表清单**，可能落后于真实模型。
  缓解：它是"期望形态"的登记处；真实模型接入时应以迁移为准并同步此清单。
- 目前没有真实迁移执行与回滚演练（属 P2/P3 的 sandbox 交付物）。

## 触发重新评估的条件

1. 目标环境确定后需要真实迁移工具（Alembic / 自研 runner）与回滚演练；
2. owner 划分变化（例如 security-gateway 拆 DMZ 入口代理与本地安全核心，见 §14.1）；
3. 需要把 JSONL journal 的真实数据迁移进 PG（迁移脚本与兼容窗口需另立 ADR）。
