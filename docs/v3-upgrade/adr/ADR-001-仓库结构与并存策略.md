# ADR-001：V3.0 与 V2.1 并存，8 个运行单元建在新目录

- 状态：**已采纳**（2026-10-04）
- 决策者：L1（架构约束层）+ 项目负责人
- 上游依据：AI_Factory_V3.0 系统架构 §9（逻辑服务与物理运行单元）、§15（Monorepo 与工程交付边界）、§16（P0 契约与骨架）
- 影响范围：仓库结构、后续所有阶段的落点

## 背景

现状是一个在产单体：`backend/`（FastAPI，158 path / 173 operation，26 个 router 无统一前缀）、
`frontend/`（React 18 + Vite 5），生产走宝塔 + systemd（域名与站点目录不入库，
私有部署环境），有真实客户数据与计费开票链路。

V3.0 要求 8 个运行单元、每 owner 独立 schema/迁移/DB role、契约优先（OpenAPI 3.1 + JSON Schema）、
分层接口（L0–L5）、数据分级与出域治理。这些要求与"26 个 router 无版本化路径、37 张表挤在单
`models.py`、靠应用层 `WHERE company_id` 隔离"的单体形态直接冲突。

## 决策

**V3.0 的 8 个运行单元建在新目录 `services/`，契约建在 `packages/contracts/`，与既有 `backend/` 并存。**

具体约定：

1. `services/` 下的每个运行单元是**独立进程**（`python -m services.<service-id>`），
   只注册自己 owner 的契约路由；不属于它的路径返回 404。
2. `packages/contracts/` 由 L1 产出，**L2 只读**；L2 需要改契约必须上报。
3. 每个 owner 只写自己的 `migrations/{owner}/`；**禁止**跨 owner 写表、跨服务 join、跨 owner 外键。
4. 迁移按**能力对齐**增量进行（V2.1 的 RAG / 渠道 / 行业包 / Hermes 运行时 → V3.0 的
   manufacturing-core / integrations / hermes-runtime），不是一次性搬迁。

## 被否决的替代方案

| 方案 | 否决理由 |
| --- | --- |
| 在 `backend/` 内原地改造 | 86 个 router 无版本化路径，改造期间无法灰度；在有真实客户的在产系统上做结构性重写，回归面不可控 |
| 另开新仓库 | 契约与实现会漂移；本仓库已有同步（watch-sync → prod bare repo）与部署链路，重建成本高且易漏 |
| 先做微服务拆分再补契约 | 与上游 §16 的顺序相反：P0 就是"契约与骨架"，先拆会固化成错误的接口形状 |

## 后果

**正面**：
- P0 纯增量，对在产系统零改动、零风险（实测：既有 64 项用例仍 0 失败）。
- 契约先冻结，后续 P1–P5 可以并行；L2/L4 能在契约边界内铺量而不改边界。
- 每个运行单元"只暴露自己的接口"是可测事实，而不是文档承诺。

**负面 / 需要管理的风险**：
- **双实现期**：在某个能力完全迁到 `services/` 之前，同一能力存在两份代码。
  缓解：每阶段在 handoff 里写明"能力对齐判据 + 旧入口下线清单"，不允许无限期并存。
- **数据一致性**：V3.0 禁止跨 owner 事务，V2.1 是单库单事务。迁移期需要明确
  "谁读谁写"，避免两边都写同一业务事实。
- **认知负担**：新人要同时理解两套结构。缓解：`docs/v3-upgrade/` 是唯一入口。

## 触发重新评估的条件

1. 上游要求从零代码库重建；
2. V2.1 计划停服；
3. 出现必须让 `services/` 与 `backend/` 共享数据库事务的场景
   （按 V3.0 设计不应出现；若出现说明 owner 划分需要重做，而不是合并事务）。
