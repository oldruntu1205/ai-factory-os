# ADR-003：阶段门禁分域（P0 门禁不看 P1 契约）

- 状态：**已采纳**（2026-10-04）
- 触发：P1 落地时，P0 契约门禁因新增 `openapi/p1.openapi.json` 而误报
- 影响范围：`tests/contracts/`、`scripts/gate*.py`、所有后续阶段的门禁

## 背景

P0 的静态门禁 `tests/contracts/test_p0_contracts.py` 原来这样发现契约文件：

```python
for directory in READ_ROOTS:            # openapi/ 与 schemas/
    for file in sorted(directory.rglob("*")):
        ...
# 然后断言：OpenAPI 里的接口合集 == P0 清单（严格相等）
```

P1 按契约优先原则在**同一个** `packages/contracts/` 下新增了 6 个接口，
于是 P0 门禁报「接口合集不等于 P0 清单」并失败。

这不是 P1 的错，也不是 P0 的错——是**门禁缺少阶段分域**。

## 决策

1. **P0 门禁只看 P0 契约集合**：`Documents` 改为按显式文件名清单读取
   （`P0_OPENAPI_FILES` / `P0_SCHEMA_FILES`），不再 rglob 整个目录。
2. **P1 门禁负责证明 P0 没被动过**：`test_p1_contracts.py` 用 sha256 常量锁定
   P0 的 12 个契约文件**原始字节**，任何改动立即报红。
3. **门禁脚本阶段感知**：`scripts/gate.py --stages p0,p1`；
   `scripts/gate_p0.py` 保留为 `--stages p0` 的等价入口。
4. **共享服务上出现新阶段路径是正常的**：P1 的新接口按设计挂在同一个
   security-gateway / manufacturing-core 上。因此 **P0 门禁的「契约外路径」断言
   不覆盖 P1 路径**；"只暴露自己 owner 的接口、不新增接口层"由 P1 运行验收负责。

## 为什么不是把 P0 文件搬进 `packages/contracts/frozen/p0/`

考虑过，否决。P1 契约用**相对路径**引用 P0 契约（`common-context.json`、
`../schemas/p1-*.json`、`p0.openapi.json#/components/...`），实测有 30+ 处。
搬目录会让所有引用失效，需要改写 P1 契约——**改动面远大于收益**。

用「显式文件清单 + 哈希锁定」达到同样的保证，且不动任何契约文件。

## 后果

**正面**
- 每个阶段的门禁互不污染；后续 P2/P3 沿用同一模式。
- P0 契约被**字节级**冻结（哈希），比"接口集合相等"更强。
- 阶段边界显式记录在测试源码的注释里，而不是靠约定。

**负面 / 需要管理**
- 新增契约文件必须同时在对应测试的清单里登记，否则不被门禁覆盖。
  缓解：`test_contract_meta_validation.py` 按目录发现（不分阶段），
  对所有契约做元模式校验，形成第二道网；`test_p0_original_bytes_are_locked`
  里还有 `existing - P1_FILES == set(P0_SHA256)` 的"未经基线锁定"断言。
- `scripts/gate_p0.py` 与 `scripts/gate.py` 两个入口。缓解：前者只做转发，逻辑唯一。

## 触发重新评估的条件

若将来契约需要**跨阶段复用文件**（例如 P2 修改 P1 定义的 schema），
则应改为「契约按主版本分目录 + 兼容性断言」，而不是继续加文件清单。
