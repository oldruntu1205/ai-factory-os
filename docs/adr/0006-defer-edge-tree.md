# ADR-0006 · 延后 `edge/` 独立部署树，Edge 语义先在 kernel 内落地并验证

- 状态：**已接受（延后）**
- 日期：2026-10-05
- 上游依据：§15 布局含 `edge/agent/`、`edge/inference/`、`edge/guard/`、`edge/adapters/`；
  §8「**Edge 节点不计入这 8 个核心应用单元**」；
  §14.1「`/edge/v1/**` 属现场 API，中心服务不注册……生产由 Edge Gateway 承载」

## 背景

上游 §15 列了四个 `edge/` 子目录，同时明文说明 **Edge 节点不计入 8 个核心应用单元**。

现场语义（Guard 判定阶段与优先级、影子不产生动作、互锁不可被置信度覆盖、
spool 只补报事实、断连自治需有效发布）是**P4 的核心内容，必须现在做**；
但"把这些代码放进 `edge/` 目录"是**部署形态**问题。

## 决策

**分两步：语义先立，部署树后置。**

1. **现在（已完成）**：Edge 语义在 `services/_kernel/edge.py` 与
   `packages/domain/guard.py` 实现并验证。
   - `/edge/v1/**` 路由在本地挂在 `manufacturing-core` 上
     （`EDGE_OWNER_SERVICE`），仅供本地验证；
   - 阶段与原因码词表放 `packages/domain`（唯一真相源，
     观测侧与现场侧共用，并有漂移探针）。
2. **后置**：`edge/` 目录树与 Edge Gateway 的真实打包方式，
   随 P5（受限生产）与现场许可一起做。

## 后果

**好处**

- 语义**已经在门禁里**（A09/A10 有真实多进程断言：
  影子不产生动作、守卫按顺序拒、高置信不能绕过互锁、
  spool 已执行事实不可被中心执行、断连需有效发布）。
- 避免了"先建一堆空目录"，那种结构看起来完成、实际上什么也没验证。

**代价（如实记录）**

- **`edge/` 目录仍然缺失**，`ls edge/` 会显示不存在。这是**有意为之**，
  不是遗漏——本 ADR 就是它的书面依据。
- Edge 的真实部署形态（现场主机、协议适配、离线打包、
  许可与签名策略的落地）**未冻结**，属外部依赖。
- 上游要求「Edge 优先 Python」——当前实现是 Python，满足；
  但"Edge 侧如何与中心共享 `packages/domain`"（打包含入还是复制）
  **尚未确定**，已记在 `P2-共享领域包.md` 的已知限制里。

## 备选方案与不选的理由

| 方案 | 为什么不选 |
| --- | --- |
| 现在就建 `edge/{agent,inference,guard,adapters}/` 四个目录 | 会产出**没有验证内容的骨架**。上游 P0 确实要骨架，但 Edge 属 P4/P5；空目录给人"已完成"的错觉，比缺失更糟。 |
| 把 kernel 里的 Edge 代码直接搬进 `edge/` | 搬运会打断"观测侧与现场侧共用同一份词表"（那是刚修的漂移缺陷），且无任何收益——部署形态还没定。 |
| 现在就确定打包方式 | 缺现场主机与部署约束，现在定就是猜；猜出来的打包方式会成为后续的负债。 |
