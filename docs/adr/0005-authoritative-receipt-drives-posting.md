# ADR-0005 · 只有权威执行回执能说"已过账"，且两个命令视图不混形状

- 状态：**已接受**
- 日期：2026-10-05
- 上游依据：§6「**控制台显示需带状态来源和更新时间，防止 UI 显示成功而 ERP 未过账**」；
  §17 A14「任务成功只由权威执行回执驱动，accepted/未知不显示已过账」

## 背景

系统里同时存在四种"看起来像成功"的东西，而它们的含义**完全不同**：

| 字段 | 它其实只表示 |
| --- | --- |
| `task.status = SUCCEEDED` | 编排跑完了 |
| `command.status = SUCCEEDED` | 执行侧认为成功了 |
| `business_success = true` | 业务成功了（由权威回执驱动） |
| `posting_status` | **账务是否真的过账** |

把它们混着显示，就会出现上游点名要防的那种事故：
**界面显示成功，而 ERP 根本没记账。**

## 决策

### 1. 只有权威回执能说"已过账"

判定实现为**默认一切未确认**：除非 `authority_verified === true`
且 `posting_status === "POSTED"`，否则不显示"已过账"。

反过来写（默认成功、有异常才降级）会让"**没拿到回执**"显示成成功——
那恰恰是要防的那件事。

- `UNKNOWN` **单独显示**「结果未知，需对账」，不得含糊成"处理中"
  （未知意味着"可能已经执行了"，需要人工查，而不是等它自己好）。
- `NOT_APPLICABLE` 与「未过账」分开——一个是"压根没有账务动作"，
  一个是"本该过账但没成"。

### 2. 每条结论都带来源与更新时间

`task` / `command` / `receipt` 各自的状态、来源、更新时间**分别列出**，
缺信息时如实留空。上游明文要求这一点，它也是"结论可审计"的实际含义。

### 3. 两个命令视图不混形状——这是实测纠正过的

| 接口 | 契约 | 有 `posting_status`？ |
| --- | --- | --- |
| `GET /internal/v1/commands/{id}` | `command-status.json`（16 字段，`additionalProperties: false`） | **否** |
| `GET /internal/v1/commands/{id}/execution-record` | `p3-command.json#/$defs/View` | **是** |

联调时我曾把 P3 字段塞进前者"顺手加全"，结果被
`test_responses_conform_to_contract_schemas` 当场报红。
**正确修法是读对接口，不是改宽契约。**

### 4. 缺数据时说缺

`posting_status` 在当前实现里**恒为 `NOT_CONFIRMED`**（5 处回执构造全部写死），
因为真实的过账凭证（ERP 确认）是外部依赖。

**这不是缺陷**：界面对一条刚跑完的命令显示「未过账」，
**正是本条决策要的效果**。

## 后果

**好处**

- A14 有**可执行判据**：穷举"任务成功 × 命令成功"的所有组合，
  在没有回执时**一律不得** POSTED；编排成功但无回执时理由写明"未取得权威过账回执"。
- 列表页的汇总**走同一个判定出口**（禁止自己按 `task.status` 再数一遍）——
  否则同一屏会出现两个互相矛盾的数字，而**没人知道哪个对**。

**代价（如实记录）**

- "已过账"在真实凭证接入前**不可达**，因此这一整条链路的生产侧
  只有"未过账"一种实测结果。这是**刻意的**，不是没做完。
- 后台目前只覆盖任务结论、命令回执、批准可决定性三块；
  员工/发布/对账页面未做。
- **未做浏览器端到端**（无头截图 / DOM 断言）：
  验证的是"HTTP 200 + 真实 API 数据 + 判定正确"。

## 备选方案与不选的理由

| 方案 | 为什么不选 |
| --- | --- |
| 默认成功、有异常才降级 | 「没拿到回执」会显示成成功——正是上游要防的那种事故。 |
| 不区分 `NOT_APPLICABLE` 与 `NOT_CONFIRMED` | 看的人会以为"本该过账却没成"，而实际是"压根没有账务动作"，会引发错误的追查方向。 |
| 把 P3 字段并进 P0 视图"一次给全" | 违反 `additionalProperties: false` 的契约；契约拦下我是对的。 |
| 让界面自己算结论 | 与 `src/status.js` 形成两套口径，分叉后同一屏数字互相矛盾。 |
