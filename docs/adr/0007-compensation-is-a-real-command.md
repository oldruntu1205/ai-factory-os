# ADR-0007 · 补偿命令也是真命令：不得伪造权威回执来"走完"流程

- 状态：**已接受**
- 日期：2026-10-05
- 上游依据：§5（Saga 补偿）、§6「**防止 UI 显示成功而 ERP 未过账**」、
  §17 A08（补偿失败进人工队列）/ A14（只有权威回执驱动成功）；
  与 [ADR-0005](0005-authoritative-receipt-drives-posting.md) 同源

## 背景

2026-10-05 审计发现：`_handler_p3_saga_compensate` 的常规补偿分支
**直接写上一份 `authority_verified: True, business_success: True` 的回执**，
并把步骤标成 `command_status: "SUCCEEDED"` —— 而那条补偿命令
**从未派发、从未执行、也没有任何回执**。

它同时违反三条已确立的约束：

1. **核心不变量**：只有真实执行产生的权威回执能驱动成功（ADR-0005）；
2. **一数一源**：命令的最终状态归 Transaction，步骤账不能自己当权威；
3. **可核对性**：那份回执的 `command_id` 是**另起一个 uuid4** 生成的，
   与步骤自己的补偿命令 id 不同——照回执去查命令会查不到。

**净效果**：整单在"什么都没做"的情况下报 `COMPENSATED`。

A08 的既有用例**走完了整条路径并断言 `COMPENSATED`**，因此一路通过——
它断言的是"流程能走完"，而不是"**走完的依据是不是真的**"。

## 决策

**补偿是一条真命令，它的成功必须靠真实回执挣来。**

具体三条：

1. **受理态 ≠ 成功态**：补偿受理时 `command_status = "AUTHORIZED"`、
   `authority_receipt = None`；与 `_p3_accepted` 同一口径。
2. **登记真实命令记录**：补偿命令必须存在于命令存储中，
   能像其它命令一样取租约、执行、收敛。
   只在步骤账里写个 `command_id` 字符串是不够的——那既不能执行也无法核对。
3. **判定凭已验证回执**：`all_compensation_receipts_verified` 要求
   （a）终态 `SUCCEEDED`、（b）`authority_verified is True`、
   （c）**回执的 `command_id` 与补偿命令是同一个**。

附加决定：**补偿需要明确批准**。补偿工具是 R2，而 R2 的复核会拒绝无批准的执行。
这**是对的**——补偿会改动账务，不能因为"它是撤销"就自动获得授权。

## 后果

**好处**

- `COMPENSATED` 是**挣来的**：它只有在补偿命令真的走完并取得权威回执后才可能成立。
- 回执与命令 id 一致，**可核对**（旧实现核不上账）。
- 顺带修掉一个"永远达不到"的 bug：步骤账只记受理时的快照，
  而进展写在命令上；不投影就永远显示 `AUTHORIZED`。
  现在由 `_compensation_live_state()` 从命令存储投影实时状态。

**代价（如实记录）**

- **补偿的批准人是硬编码的 `user-approver`**：真实部署必须来自人（SSO 未接入，见 ADR-0004）。
- **补偿没有真正派发到外部系统**：它走"取租约 → 执行 → 收敛"的受控路径，
  收敛时的源系统结论由调用方给出。真实 MES/WMS/ERP 的派发与回执属外部依赖。
- **既有用例被迫升级**：`test_saga_requires_physical_restore_...` 从"走完"改成
  "**驱动真实收敛**"。这是修缺陷的正常代价——**不改测试就等于把伪造固化成期望**。

## 备选方案与不选的理由

| 方案 | 为什么不选 |
| --- | --- |
| 保留伪造，只在文档里记一笔 | 它是**审核/看板会读到的字段**。"已知的假成功"与"未知的假成功"一样危险，而且会随代码复制扩散。 |
| 只修 `command_id` 不一致（最小改动） | 治了症状：**没派发却说成功**这件事本身才是要害。 |
| 在 `_p3_saga_view` 里加校验但不改处理器 | 会让既有用例红，但**不改变系统行为**——补偿依然不会真的执行。治了报告，没治病。 |
| 让补偿绕过批准（因为它"只是撤销"） | 补偿会改动账务；"撤销"不是免于授权的理由。上游要求 R2 明确批准。 |
